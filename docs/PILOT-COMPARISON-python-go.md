# Сравнительный отчёт: Python vs Go (пилот)

Оба пилота — 3 тикета на язык, метод из CLAUDE.md. Python идёт в
доклад RubyRussia 2026, Go — нет (данные про запас, см. CLAUDE.md,
«Языки вне доклада»). Три раунда прогонов на обоих языках: раунд 1
(2026-08-19/20, старый харнесс — внутренняя песочница Claude Code
через `--settings`), раунд 2 (2026-08-24, Docker-обвязанный харнесс,
но без явно зафиксированного `--effort` — дефолт CLI оказался `high`),
раунд 3 (2026-08-24/25, `--effort xhigh` явно) — **канонические
данные**. Ниже — сравнение по каноническим (раунд 3) прогонам, с
историческими раундами 1–2 отдельно для прозрачности методики, не как
альтернативный источник правды. Полная построчная запись, включая
аннулированные попытки всех трёх раундов, — в
[`docs/EXPERIMENT-LOG.md`](EXPERIMENT-LOG.md).

«Время» везде ниже — `duration_ms` конкретного вызова `claude -p`
(точное определение — раздел «Лог» в [CLAUDE.md](../CLAUDE.md)), не
календарное время работы над тикетом: не включает паузы между
попытками (переигровки, ожидание решений человека по ходу пилота,
включая паузу на сброс рейт-лимита в раунде 3) и не может их включать
— headless-вызов не имеет точки, где мог бы остановиться и ждать
кого-то.

Модель и effort — зафиксированы явно с раунда 3 (`--model
claude-sonnet-5 --effort xhigh` в `scripts/run-pilot-ticket.sh`), не
просто предположены: проверено `grep` по всем шести каноническим
транскриптам — `effort: xhigh` на каждом. До раунда 3 харнес не
передавал `--effort` вообще: раунд 1 (полагался на дефолт CLI,
задокументированный тогда как `xhigh`) и раунд 3 совпадают по effort,
раунд 2 — нет (`high`), обнаружено только `grep`-проверкой по
транскриптам раунда 2, не по документации CLI (см. раздел «Effort
задокументирован, но раньше не фиксировался» ниже). Известный,
принятый как есть побочный эффект headless-режима на всех раундах:
каждый вызов несёт небольшое сопутствующее использование
`claude-haiku-4-5` (~1500 токенов, ~$0.0015, видно в `modelUsage`
результата отдельно от основного `usage`) — устранить без `--bare`
(ломает OAuth-аутентификацию, см. CLAUDE.md) не удалось, но одинаково
на каждом вызове, не искажает сравнение между языками. Долларовая
стоимость сама по себе малоинформативна без токенов (конфлирует
четыре категории с разной ценой за единицу) и без явной фиксации
модели/effort — токены приведены отдельно в таблице ниже, не только
доллары.

## История: харнесс и effort не были идентичны между раундами (закрыто)

Не для того, чтобы застрять на прошлом — чтобы показать, что итоговое
«канонический прогон» не взято с потолка, а результат двух реальных,
найденных и закрытых методологических дыр.

**Раунд 1 → раунд 2 (харнесс).** Python и Go в раунде 1 прогонялись
под разными версиями `scripts/run-pilot-ticket.sh` (Go получил фиксы
`sandbox.allowUnsandboxedCommands`/Docker-сети раньше Python) — это
уже делало прямое сравнение раунда 1 небезупречным. Более серьёзная
находка (2026-08-21): вся файловая песочница Claude Code, на которой
держался весь раунд 1, структурно не покрывала инструменты Read/Write
— граница была иллюзорной, хотя построчный аудит транскриптов не
нашёл фактической эксплуатации ни на одном из 13 прогонов раунда 1
(разбор — [docs/incidents/2026-08-21-write-tool-sandbox-escape/](incidents/2026-08-21-write-tool-sandbox-escape/README.md)).
Фикс — весь `claude -p` внутри Docker-контейнера (`pilot-harness:latest`)
с единственной примонтированной директорией пилота; оба языка
переиграны под ним в раунде 2 (2026-08-24).

**Раунд 2 → раунд 3 (effort).** Харнес после перехода на Docker-обвязку
по-прежнему не передавал `--effort` явно — полагался на дефолт CLI.
Раунд 1 задокументирован под `effort: xhigh` (проверено по
транскриптам на момент того пилота). Раунд 2 (2026-08-24) оказался под
`effort: high` — дефолт CLI сам сдрейфовал между версиями Claude Code
(харнес закреплён на `@anthropic-ai/claude-code@2.1.238`, версия сама
по себе не менялась в процессе, но её дефолт effort отличался от того,
что было у более ранней версии, использованной в раунде 1). Найдено
только `grep`-проверкой `"effort":"..."` по архивированным
`transcript.jsonl` раунда 2 — не по `--help`, не по документации, не
по предположению «раз задано один раз, значит не менялось» (тот же
принцип, что уже применялся к модели и токенам в этом отчёте).
Фикс — `--effort xhigh` явно в `scripts/run-pilot-ticket.sh`, оба
языка переиграны в раунде 3 (2026-08-24/25). Раунд 3 также дал первый
живой сигнал риска 3 пилотной фазы (рейт-лимит `429 session limit` на
Go, тикет 2, первая попытка) — см. `docs/PILOT-RESULT-go.md`.

Итог: раунд 3 — первый раунд, где Python и Go прогонялись под
буквально идентичной, полностью зафиксированной конфигурацией
(модель, effort, харнес, изоляция) от начала до конца. Обе более
ранние оговорки этого отчёта («харнесс не идентичен между языками»,
«effort не зафиксирован явно») сняты, не отложены.

обоснован тремя тикетами на язык).

входит в «канонические» — сдался, не сошёлся): Go — 14.1 мин, $2.82,
4 прогона вместо 3. Честная стоимость этого раунда для Go с учётом
реального сбоя инфраструктуры, не только удачных попыток.

## Соответствие спецификации

Отклонений от `docs/SYNCBOX-SPEC.md`/`docs/syncbox-openapi.yaml` не
найдено ни на одном тикете ни одного языка ни в одном из трёх раундов:
HTTP-коды и форма JSON совпадают дословно, границы тикетов соблюдены в
обе стороны (ни один самоотчёт не забежал вперёд на
traversal-защиту/атомарность/DELETE, ни один не пропустил часть
объявленного тикета). Риск 2 пилотной фазы («соответствие спецификации
между языками», CLAUDE.md, «Сначала пилот») пока не даёт повода для
тревоги — но и настоящего сравнения пока нет, потому что сравнивать не
с чем: оба языка одинаково точны.

## Поведенческие отличия (наблюдение по существу гипотезы, не находка методики)

- **Штатные тесты.** В раунде 1 Go написал юнит-тесты на всех трёх
  тикетах без явного требования в промпте, Python — ни одного (каждый
  раз проверял вручную через `curl`). Начиная с раунда 2 оба языка
  пишут тесты на всех тикетах — 2026-08-20 `SYNCBOX-SPEC.md` стал
  явно требовать штатные тесты (раздел «Критерии приёмки»), это
  изменение спецификации, а не изменение языкового поведения модели —
  раунд 1 прошёл до этой правки. Различие раунда 1 остаётся
  интересным наблюдением само по себе (какой язык модель тестирует
  «по умолчанию», без явного требования), просто больше не
  воспроизводится с раунда 2, потому что вопрос закрыт явным
  требованием в спецификации.
- **Формат `modified_at`.** Устойчиво воспроизводится на независимых
  генерациях кода: Go — `...Z` без дробных секунд, Python — `...Z` с
  микросекундами. Оба валидны как ISO 8601 UTC, спецификация не
  требует конкретного формата строки — не нарушение, разные конвенции
  по умолчанию в стандартных библиотеках (Go `time.Format(time.RFC3339)`
  по умолчанию не даёт дробных секунд, Python `datetime.isoformat()` —
  даёт микросекунды).
- **Внутренние шаги (`num_turns`).** Канонический раунд (3): Python
  30→27→25 (устойчиво убывающий тренд), Go 38→24→37 (не монотонно —
  тикет 3 включал рейт-лимитную заминку тикета 2 непосредственно
  перед собой в рамках того же сеанса работы, могло повлиять на объём
  контекста; отдельно от заминки — метрика зашумлена харнесс-трением
  сильнее, чем у Python, тот же паттерн наблюдался и в раунде 1).

## Code security (исключено)

Проверили и убрали из метода — вот почему. Первый прогон (раунд 1)
дал:

| Язык   | Security-находок | Из них HIGH |
| ------ | ---------------- | ----------- |
| Python | 1 (bandit)       | 0           |
| Go     | 14 (gosec)       | 4           |

На вид — «Go менее безопасен на порядок». Проверил это перед тем, как
записывать как наблюдение, и вывод не подтвердился:

- **Path traversal — не языковой эффект, а разница покрытия
  инструментов.** У Python `server/app.py` строит путь на диске ровно
  тем же небезопасным способом, что и Go (`os.path.join(data_dir,
  key)` без проверки `key` на `..`/абсолютный путь) — тот же
  сознательно отложенный до тикета 5 пробел, один в один. `gosec`
  ловит его четырьмя находками HIGH (`G703`, taint-анализ). У `bandit`
  в дефолтном наборе правил такого чекера просто нет — проверил
  напрямую: собрал синтетический Python-файл с идентичным паттерном
  (`os.path.join` + Flask-роут без валидации ключа) и прогнал через
  `bandit` — **0 находок**. У Python в коде ровно та же дыра, просто
  инструмент её не видит.
- Кодовые базы разного размера и стиля (Go многословнее по
  конструкции) — количество находок не нормировано на объём кода, что
  дополнительно искажает сравнение даже без разницы в покрытии правил.

**Решение:** code security исключён из метода (CLAUDE.md, раздел
«Метод», пункт 4) — не отложен, а отвергнут по итогам этой проверки.
Не пересматривался при переходе на раунды 2–3 (харнесс/effort не
относятся к причине отказа).

## Рекомендация

Обе методологические оговорки, из-за которых предыдущая версия этого
отчёта не считала себя окончательным сравнением («харнесс не идентичен
между языками», «effort не зафиксирован явно»), закрыты в раунде 3 —
Python и Go теперь прогнаны под буквально одной, полностью
зафиксированной конфигурацией от начала до конца. Раунд 3 — первый
раунд, пригодный как база для сравнения с последующими языками пилота
(Ruby следующий по методу CLAUDE.md, «Сначала пилот»). Три тикета на
язык — по-прежнему слишком мало для статистической значимости
(CLAUDE.md прямо это подчёркивает), выводы этого отчёта — наблюдения
пилотной фазы, не результат.

Единственный не закрытый из трёх исходных рисков пилотной фазы —
устойчивость цикла `-p`/`--resume` к рейт-лимитам (риск 3): раунд 3
дал первый живой сигнал (см. `docs/PILOT-RESULT-go.md`), но не
полноценный стресс-тест — ни один тикет пока не потребовал реального
цикла `--resume` внутри одной сессии ревью-фикс-ревью. Следующий язык
пилота стоит держать под тем же наблюдением (`grep` по `effort` в
транскриптах, проверка сигналов рейт-лимита в `--output-format json`),
не считать закрытым автоматически на основании одного прецедента.
