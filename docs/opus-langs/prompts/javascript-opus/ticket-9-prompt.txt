Продолжаем проект Syncbox (тикеты 1-8 — каркас сервера, happy path для PUT/GET блоба, список блобов, удаление блоба, защита от directory traversal, атомарность записи при параллельных PUT, клиент push, клиент pull — уже сделаны в этом же репозитории, плюс несколько фиксов серверной обработки граничных значений key). Тикет 9: клиент, команда status (dry-run).

Полная спецификация — в файлах SYNCBOX-SPEC.md и syncbox-openapi.yaml в корне этого репозитория — прочитай перед началом, если нужно освежить детали.

Нужно реализовать:

- Команду syncbox status <dir> --server <url> у CLI-клиента (исполняемый файл syncbox, см. раздел «CLI (обязательный контракт)» спецификации): сравнить содержимое <dir> со списком блобов на сервере (GET /blobs) по относительному POSIX-пути (key) и SHA-256, и напечатать отчёт о том, что сделал бы sync, НИЧЕГО не меняя — ни локально, ни на сервере:
  - файлы, которые были бы загружены на сервер (есть локально, а на сервере отсутствуют или отличаются по SHA-256) — направление push;
  - файлы, которые были бы скачаны с сервера (есть на сервере, а локально отсутствуют или отличаются по SHA-256) — направление pull.
- status строго read-only: ни одного PUT/DELETE на сервер, ни одного создания, изменения или удаления локального файла. GET /blobs и GET /blobs/{key} для сравнения — можно; всё, что меняет состояние любой из сторон, — нельзя.
- Ключ блоба — относительный POSIX-путь файла внутри <dir> (та же конвенция key, что на сервере, в push и в pull).
- Формат вывода — на твоё усмотрение (спецификация его не фиксирует), но он должен быть человекочитаемым и различать направление: что ушло бы на сервер (upload) и что пришло бы с сервера (download). Отсутствие расхождений — тоже валидный, понятный вывод.
- Код возврата 0, когда сравнение выполнено успешно, независимо от того, есть расхождения или нет: status их показывает, а не «исправляет».
- --server обязателен; то же значение можно задать переменной окружения SYNCBOX_SERVER — как описано в спецификации.
- Обёртка запуска: исполняемый файл run-client в корне репозитория уже принимает все четыре подкоманды по интерфейсу; теперь run-client status <dir> --server <url> должен выполнять реальную работу вместо сообщения «пока не реализовано».
- Штатные тесты на новую функциональность обязательны (раздел «Критерии приёмки» спецификации) и запускаются через уже существующую обёртку run-tests — покрой ими как минимум: status показывает верное направление для локально-нового файла, для серверно-нового файла и для файла, разошедшегося по содержимому; status не меняет ни сервер, ни локальную ФС.
- Клиент, как и сервер, исполняется в Docker-контейнере через docker compose, не напрямую на хосте — то же требование раздела «Docker-изоляция», уже выполненное для push и pull.

Границы этого тикета:

- sync — отдельный следующий тикет (10), не входит. status только печатает предполагаемые действия; двунаправленное применение изменений и правило разрешения конфликтов из спецификации — это тикет 10. run-client должен по-прежнему принимать sync по интерфейсу (sync <dir> --server <url>), но для него остаётся понятное сообщение о том, что команда пока не реализована, и ненулевой код возврата — вместо необъяснимого падения.
- Полная обработка сетевых ошибок и частичных сбоев (недоступный сервер, часть запросов не прошла) — отдельный будущий тикет (11), не входит. Базовая реакция на явный сбой (например, сервер недоступен) должна быть вменяемой — не проходить молча и не зависать, — но не обязана покрывать весь объём раздела «Коды возврата и ошибки» спецификации (детальный формат отчёта по частичным сбоям, коды возврата под конкретные случаи) — это тикет 11.

Не реализовывай перечисленное выше заранее — не входит в объём этого тикета.

Библиотеки, HTTP-клиент и внутреннее устройство — на твоё усмотрение, как и в предыдущих тикетах.

Версия языка в этом проекте зафиксирована: Node.js 20, базовый Docker-образ node:20-alpine (FROM node:20-alpine в Dockerfile). Не меняй версию языка и базовый образ.
