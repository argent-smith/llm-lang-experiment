Проверка HTTP-поверхности сервера снаружи — формальным перебором мусорных и граничных значений key по схеме API — нашла баг в текущей реализации (сервер Syncbox, тикеты 1-7 уже сделаны в этом же репозитории). Нужно исправить.

Симптом: PUT /blobs/{key}, где key после декодирования percent-encoding содержит необычные байты — управляющие символы диапазона C1 (например, %C2%8E → U+008E), символы из дополнительных плоскостей Unicode (например, %F3%9C%B8%A0), высокие байты Latin-1 — возвращает HTTP 500 вместо задокументированных в syncbox-openapi.yaml кодов 201 (блоб записан) или 400 (key отклонён). Пример запроса, дающего 500:

    curl -X PUT --data-binary 'x' 'http://<server>/blobs/e1%C2%8E%C2%B6%F3%9C%B8%A0'

Похоже, структурная валидация key (сегмент .., абсолютный путь, null-байт, корректность UTF-8, выход за пределы корня хранилища) проходит успешно, а затем сама запись блоба на диск (write / rename / fsync временного или целевого файла) падает с ошибкой уровня ОС — EIO, ENOENT сразу после успешного с виду write, OSError/errno про «invalid or incomplete multibyte character» и т. п. — и эта ошибка нигде не перехватывается: обработчик отдаёт общий 500.

Нужно:

- Обернуть запись блоба так, чтобы неспособность сервера сохранить файл для данного key давала 400 (key невалиден) с понятным сообщением — а не неперехваченный 500. Контракт PUT /blobs/{key} — только 201 или 400; 500 недопустим ни на каком значении key.
- Не хардкодить конкретные байтовые последовательности из симптома — обрабатывать общий класс: любой key, который в итоге не удаётся записать на диск, → 400.
- Обычные ключи (плоские и вложенные) должны по-прежнему давать 201; уже реализованное отклонение traversal / .. / абсолютного пути / null-байта — по-прежнему 400. Штатные тесты проекта не должны сломаться, добавь тесты на этот случай.
- После фикса — самостоятельно перепроверь на сервере, поднятом через run-server: PUT /blobs/<такой key> больше не даёт 500 (даёт 400, либо 201, если файл реально удаётся записать), обычный PUT/GET-раунд-трип работает, штатные тесты зелёные. Учти, что часть таких ошибок ОС может быть неустойчивой (проявляться не на каждом одинаковом запросе) — фикс должен закрывать любой сбой записи блоба, а не конкретный воспроизводящийся случай.

Остальная функциональность сервера уже реализована и не нуждается в изменениях — правь только эту конкретную проблему.
