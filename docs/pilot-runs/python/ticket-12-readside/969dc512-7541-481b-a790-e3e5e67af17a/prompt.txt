Проверь текущую реализацию сервера Syncbox (тикеты 1-7 уже сделаны в этом же репозитории) на соответствие HTTP API из syncbox-openapi.yaml для граничных и мусорных значений key — percent-encoded последовательности, декодирующиеся в управляющие символы, символы из дополнительных плоскостей Unicode, высокие байты Latin-1, символы новой строки и возврата каретки в пути.

Если сервер на каком-либо таком key отвечает кодом вне схемы — в частности любым 5xx, либо кодом, не входящим в список ответов операции (для PUT /blobs/{key} схема допускает 201 и 400; для GET и DELETE — 200/204/404 и 400) — найди причину и почини по существу.

Требования к фиксу:
- Обрабатывай класс проблемы, не конкретные байтовые последовательности. Любой key, который сервер не может ни сохранить, ни прочитать, ни удалить, ни даже маршрутизировать по своему пути — это 400 (key невалиден), а не падение и не необъяснимый 404.
- Обычные ключи (плоские и вложенные) должны по-прежнему давать 201/200/204; уже реализованное отклонение traversal/`..`/абсолютного пути/null-байта — по-прежнему 400.
- Добавь автоматические тесты на эти случаи (в том числе позитивные: легитимный key с необычной, но валидной подстрокой не должен блокироваться).
- Ничего сверх перечисленного не меняй.

После фикса перепроверь сам: подними сервер через run-server и прогони run-tests.
