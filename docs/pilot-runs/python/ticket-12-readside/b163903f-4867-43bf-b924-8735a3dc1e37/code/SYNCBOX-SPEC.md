# Спецификация: Syncbox

Спецификация проекта Syncbox, реализуемого с нуля. HTTP API и CLI
фиксированы буквально, вплоть до имён флагов и переменных окружения.
Внутреннее устройство (выбор библиотек, формат хранения метаданных,
модель конкурентности, фреймворк тестирования) — на усмотрение
реализации: важно только внешнее поведение.

## Назначение

Syncbox — минимальное самостоятельно хостящееся файловое хранилище с
синхронизацией: HTTP-сервер хранит блобы на диске, CLI-клиент сравнивает
локальную папку с содержимым сервера по контрольным суммам и
синхронизирует разницу. Компактный аналог связки rsync + самодельный S3.

Два компонента:

- **Сервер** — HTTP API поверх файловой системы.
- **Клиент** — CLI, обращающийся к серверу по HTTP.

## HTTP API (обязательный контракт)

Источник истины — [syncbox-openapi.yaml](syncbox-openapi.yaml) (OpenAPI
3.0): эндпоинты, коды ответов, тела запросов и ответов формально описаны
там. Таблица ниже — читаемое резюме для быстрой ориентации; при
расхождении приоритет у файла схемы, не у таблицы.

| Метод    | Путь           | Назначение                                  | Успех                                                         | Ошибки                       |
| -------- | -------------- | ------------------------------------------- | ------------------------------------------------------------- | ---------------------------- |
| `PUT`    | `/blobs/{key}` | Загрузить блоб (тело запроса — сырые байты) | `201`, JSON `{"key", "sha256", "size"}`                       | `400` при недопустимом `key` |
| `GET`    | `/blobs/{key}` | Скачать блоб                                | `200`, тело — байты                                           | `404` если не найден         |
| `DELETE` | `/blobs/{key}` | Удалить блоб                                | `204`                                                         | `404` если не найден         |
| `GET`    | `/blobs`       | Список блобов                               | `200`, JSON-массив `{"key", "size", "sha256", "modified_at"}` | —                            |
| `GET`    | `/healthz`     | Проверка живости                            | `200`                                                         | —                            |

`key` — POSIX-путь относительно корня хранилища (`docs/readme.txt`).
Сервер обязан отклонять `key`, содержащий `..` или абсолютный путь,
кодом `400` — это защита от directory traversal, а не опция. То же
касается `key`, который не удаётся представить как имя файла на
файловой системе сервера (например, из-за суррогатных пар после
декодирования) — тоже `400`, не падение сервера.

`sha256` — хеш содержимого в hex. `modified_at` — ISO 8601 UTC.

Запись на диск должна быть атомарной (запись во временный файл и
последующий rename) — параллельные `PUT` по разным ключам не должны
приводить к повреждению данных.

CLI-контракт (`run-server`/`run-client`, флаги, поведение
push/pull/sync/status) в OpenAPI не входит — стандартной схемы для CLI
нет, он остаётся прозой ниже.

## CLI (обязательный контракт)

Исполняемый файл называется `syncbox` независимо от языка реализации
(нативный бинарник, jar с обёрткой, скрипт с шебангом — не важно, лишь
бы вызывался одинаково).

| Команда                               | Поведение                                                                                                                                |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `syncbox push <dir> --server <url>`   | Обойти `<dir>` рекурсивно, посчитать SHA-256 каждого файла, сравнить со списком на сервере, загрузить отсутствующие и изменившиеся файлы |
| `syncbox pull <dir> --server <url>`   | Обратное: скачать файлы, которые есть на сервере, но отсутствуют или отличаются локально                                                 |
| `syncbox sync <dir> --server <url>`   | Двунаправленно: правило разрешения конфликтов — см. ниже                                                                                 |
| `syncbox status <dir> --server <url>` | Dry-run: напечатать, что было бы загружено/скачано, ничего не менять                                                                     |

Общие флаги: `--server <url>` обязателен везде. `--server` можно также
задавать переменной окружения `SYNCBOX_SERVER`.

Сервер конфигурируется: `--data-dir <path>` (обязателен) и `--port <n>`
(по умолчанию `8080`), либо переменными окружения `SYNCBOX_DATA_DIR` и
`SYNCBOX_PORT`.

### Правило разрешения конфликтов для `sync`

Файл считается изменённым, если его SHA-256 отличается от версии на
другой стороне. Если файл изменён и локально, и на сервере относительно
последнего известного общего состояния — побеждает более свежий
`modified_at`/mtime. При равенстве побеждает локальная версия. Это
правило фиксировано — не предмет творческой доработки, реализация должна
следовать ему буквально.

### Коды возврата и ошибки

- Недоступность сервера (сетевая ошибка, таймаут) — понятное сообщение
  в stderr, ненулевой код возврата.
- Частичный сбой (упал один файл из многих) — остальные файлы всё равно
  обрабатываются, в конце — отчёт по неудачным, код возврата ненулевой.

## Что не специфицируется намеренно

- Библиотеки и фреймворки (HTTP, тестирование, CLI-парсинг).
- Внутренний формат хранения метаданных на сервере.
- Модель конкурентности.
- Логирование, помимо обязательных сообщений об ошибках.

Свобода в этих пунктах — часть эксперимента: он должен показывать, как
язык и агент справляются в условиях, близких к обычной разработке, а
не выполняют жёстко заданную архитектуру.

## Критерии приёмки

Поскольку HTTP API и CLI зафиксированы буквально, готовность реализации на
любом языке проверяется одним и тем же чёрным ящиком, внешним по
отношению к этому репозиторию — и одним требованием к самой реализации:

- **Штатные тесты.** Каждый тикет сопровождается автоматическими
  тестами самой реализации (юнит- и/или интеграционными — конкретный
  инструмент свободен, см. «Что не специфицируется намеренно») для той
  функциональности, которую этот тикет добавляет. Это часть критерия
  готовности тикета, не опция и не факультатив. Запускаются через
  обязательную обёртку `run-tests` (см. ниже) — чтобы внешняя проверка
  могла прогнать их, не зная, какой в проекте тест-раннер и как он
  вызывается.
- **Acceptance-смок.** Поднимает сервер и клиент только через обязательную
  конвенцию запуска (`run-server`/`run-client`, см. ниже), гоняет
  `push`/`sync`/`status`/`pull` через реальный HTTP и сверяет побайтовые
  хеши — не заглядывая в код реализации.
- **Контрактная проверка.** Формальная проверка HTTP-поверхности по
  `syncbox-openapi.yaml`: генерирует тест-кейсы (включая мусорные и
  граничные значения `key`) и бьёт ими в реальный сервер, проверяя не
  сценарий использования (это к смоку), а то, что сервер не падает и
  отвечает согласно схеме на входных данных, которые сценарий не
  догадался попробовать.

Все три проверки используют только внешний интерфейс — HTTP и вызов
процесса через `run-server`/`run-client`/`run-tests` — реализации не
нужно ничего знать об их устройстве или местонахождении.

Обязательная конвенция запуска для каждой языковой реализации — без неё
чёрный ящик не сможет её вызвать:

- `<корень репозитория>/run-server --data-dir <path> --port <n>` —
  исполняемый файл, запускает сервер в текущем процессе (без демонизации).
- `<корень репозитория>/run-client <push|pull|sync|status> <dir> --server <url>`
  — исполняемый файл, форвардит подкоманду и аргументы клиенту.
- `<корень репозитория>/run-tests` — исполняемый файл, прогоняет все
  штатные тесты реализации в Docker (как и сервер с клиентом, тесты не
  запускаются напрямую на хосте) и завершается ненулевым кодом, если
  хоть один тест упал. Никаких аргументов не требует; весь вывод
  тест-раннера — в stdout/stderr.

Внутри обёртки делают что нужно реализации (интерпретатор, JAR, нативный
бинарник, `docker compose run`), снаружи вызываются одинаково независимо
от этого.

## Docker-изоляция

Обязательное условие для всех «стендов» эксперимента: и сервер, и клиент
исполняются внутри Docker-контейнеров, не напрямую на хосте, где работает
харнесс (Claude Code). Причины:

- **Воспроизводимость.** Результат не должен зависеть от того, что
  установлено на конкретной машине, где физически крутится агент.
- **Безопасность.** Код тикета, особенно на ранних, ещё не отревьюенных
  итерациях, не должен иметь неограниченный доступ к хостовой
  файловой системе.
- **Изоляция от особенностей конкретной хостовой ОС.** Поведение файловой
  системы (кодировки имён файлов, регистрозависимость, семантика rename)
  может отличаться между хостовой ОС и Linux-окружением CI/контейнера.
  Контейнер делает среду одинаковой независимо от хоста.

Внешний контракт (`run-server`/`run-client`, их аргументы) не меняется —
Docker остаётся деталью реализации внутри этих обёрток: как именно
контейнеризовать сервер и клиент, решает реализация на каждом языке,
лишь бы снаружи всё вызывалось так, как описано выше.

Всё Docker-хозяйство обязано идти через **docker compose**, не через
голые `docker run`/`docker build` в обёртках — единый источник правды
для сборки, сети и volume'ов, а не россыпь параметров, продублированных
в каждом скрипте.

## Пример стартового бэклога тикетов

Не исчерпывающий, задаёт масштаб «от каркаса до рабочего инструмента»:

1. Сервер: `/healthz`, конфигурация через флаги/переменные окружения.
2. Сервер: `PUT`/`GET` блоба (happy path).
3. Сервер: `GET /blobs` со списком и метаданными.
4. Сервер: `DELETE` блоба.
5. Сервер: защита от directory traversal в `key`.
6. Сервер: атомарность записи при параллельных `PUT`.
7. Клиент: `push`.
8. Клиент: `pull`.
9. Клиент: `status` (dry-run).
10. Клиент: `sync` с разрешением конфликтов по правилу выше.
11. Обработка сетевых ошибок и частичных сбоев на клиенте.
