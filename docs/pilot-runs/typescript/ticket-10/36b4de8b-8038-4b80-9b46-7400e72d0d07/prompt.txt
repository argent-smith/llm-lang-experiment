Продолжаем проект Syncbox (тикеты 1-9 — каркас сервера, happy path для PUT/GET блоба, список блобов, удаление блоба, защита от directory traversal, атомарность записи при параллельных PUT, клиент push, клиент pull, клиент status — уже сделаны в этом же репозитории, плюс несколько фиксов серверной обработки граничных значений key). Тикет 10: клиент, команда sync.

Полная спецификация — в файлах SYNCBOX-SPEC.md и syncbox-openapi.yaml в корне этого репозитория — прочитай перед началом, если нужно освежить детали.

Нужно реализовать:

- Команду syncbox sync <dir> --server <url> у CLI-клиента (исполняемый файл syncbox, см. раздел «CLI (обязательный контракт)» спецификации): двунаправленная синхронизация <dir> с сервером по относительному POSIX-пути (key) и SHA-256.
  - Файл, который есть только на одной стороне (локально или на сервере) или различается по SHA-256, — переносится на другую сторону: локально-новый/изменённый → PUT на сервер (как push), серверно-новый/изменённый → GET и запись в <dir> с созданием поддиректорий (как pull). По сути объединение push и pull в один проход.
  - Конфликт — файл изменился и локально, и на сервере относительно последнего известного общего состояния — разрешается строго по разделу «Правило разрешения конфликтов для `sync`» спецификации: побеждает версия с более свежим modified_at/mtime, при равенстве — локальная. Правило фиксировано, следуй ему буквально, без вариаций. modified_at сервера приходит в списке GET /blobs (поле BlobMeta.modified_at); локальный mtime — из файловой системы.
  - Механизм отслеживания «последнего известного общего состояния» между запусками — на твоё усмотрение (раздел «Что не специфицируется намеренно»): это может быть индекс/манифест, который клиент ведёт в <dir> или рядом, либо иная стратегия. При первом запуске, когда общего состояния ещё нет, расхождения разрешаются как обычные upload/download по SHA-256 (конфликта, при котором нужно правило mtime, в этот момент нет).
- sync не удаляет файлы — ни локальные, ни серверные. Как push и pull не удаляли лишнее на другой стороне, так и sync только переносит содержимое, а не зеркалит удаления. Распространение удалений спецификацией не предусмотрено.
- Код возврата 0 при успешной синхронизации.
- --server обязателен; то же значение можно задать переменной окружения SYNCBOX_SERVER — как описано в спецификации.
- Обёртка запуска: исполняемый файл run-client в корне репозитория уже принимает все четыре подкоманды по интерфейсу; теперь run-client sync <dir> --server <url> должен выполнять реальную работу вместо сообщения «пока не реализовано».
- Штатные тесты на новую функциональность обязательны (раздел «Критерии приёмки» спецификации) и запускаются через уже существующую обёртку run-tests. Покрой ими как минимум: только-локальный файл → появляется на сервере; только-серверный файл → появляется локально; файл, изменённый только локально → на сервере оказывается локальная версия; файл, изменённый только на сервере → локально оказывается серверная версия; конфликт (обе стороны изменены, разный mtime) → побеждает более свежая версия; конфликт с равным mtime → побеждает локальная.
- Клиент, как и сервер, исполняется в Docker-контейнере через docker compose, не напрямую на хосте — то же требование раздела «Docker-изоляция», уже выполненное для push, pull и status.

Границы этого тикета:

- Полная обработка сетевых ошибок и частичных сбоев (недоступный сервер, таймаут, часть файлов не перенеслась — отчёт по неудачным файлам, конкретные коды возврата под конкретные случаи из раздела «Коды возврата и ошибки» спецификации) — отдельный следующий тикет (11), не входит. Базовая реакция на явный сбой (например, сервер недоступен) должна быть вменяемой — понятное сообщение в stderr, ненулевой код возврата, не зависание, — но детальный отчёт по частичным сбоям в этом тикете реализовывать не нужно.

Не реализовывай перечисленное выше заранее — не входит в объём этого тикета.

Библиотеки, HTTP-клиент и внутреннее устройство — на твоё усмотрение, как и в предыдущих тикетах.
