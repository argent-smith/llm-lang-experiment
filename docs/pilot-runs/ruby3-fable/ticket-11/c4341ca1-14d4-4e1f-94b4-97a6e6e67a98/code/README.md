# Syncbox

Самостоятельно хостящееся файловое хранилище с синхронизацией: HTTP-сервер
хранит блобы на диске, CLI-клиент синхронизирует с ним локальную папку.
Контракт — в [SYNCBOX-SPEC.md](SYNCBOX-SPEC.md) и
[syncbox-openapi.yaml](syncbox-openapi.yaml).

Реализация на Ruby 3.3.12 (базовый образ `ruby:3.3.12`). Весь код — сервер,
клиент, тесты — исполняется только внутри Docker-контейнеров через
`docker compose`; на хосте нужны лишь `bash` и Docker с плагином compose.
Обёртки: `run-server`, `run-client`, `run-tests`.

## Состояние

Тикет 1 — каркас сервера:

- `GET /healthz` → `200`, `{"status":"ok"}`;
- конфигурация через `--data-dir <path>` (обязателен) и `--port <n>`
  (по умолчанию `8080`) либо `SYNCBOX_DATA_DIR` / `SYNCBOX_PORT`
  (флаг имеет приоритет над переменной);
- Dockerfile, `compose.yaml`, обёртки `run-server` и `run-tests`.

Тикет 2 — happy path блобов:

- `PUT /blobs/{key}` — тело запроса это сырые байты блоба (любой или
  отсутствующий `Content-Type`, `Content-Length` или chunked). Ответ `201`,
  JSON `{"key","sha256","size"}`: `sha256` — hex-хеш содержимого, `size` —
  размер в байтах. Повторный `PUT` по тому же `key` перезаписывает блоб.
- `GET /blobs/{key}` → `200`, `application/octet-stream`, байты блоба;
  `404` (JSON `{"error":"not_found"}`), если блоба нет.
- `key` — POSIX-путь относительно корня хранилища, может содержать
  вложенные каталоги (`docs/readme.txt`); блоб хранится в
  `<data-dir>/<key>` как обычный файл, промежуточные каталоги создаются
  по мере необходимости. `key` в URL может быть percent-encoded
  (`dir%20name/%D0%BF.txt`), `/` при этом не декодируется.
- Тело запроса и ответа передаётся потоково, кусками по 64 KiB, без
  загрузки всего блоба в память.

Тикет 3 — список блобов:

- `GET /blobs` → `200`, JSON-массив объектов
  `{"key","size","sha256","modified_at"}` для всех блобов на сервере,
  отсортированный по `key`. Пустое хранилище — `[]`.
- `key` — POSIX-путь относительно корня хранилища, включая вложенные
  каталоги (`docs/readme.txt`); `size` — байты; `sha256` — hex-хеш
  содержимого; `modified_at` — mtime файла в ISO 8601 UTC с точностью до
  секунды (`2026-10-05T22:38:46Z`).
- Источник истины — файловая система: в список попадают все обычные файлы
  под каталогом данных, в том числе положенные туда мимо API и dot-файлы.
  Пропускаются каталоги, FIFO и прочие не-файлы, служебный `.syncbox-tmp` и
  имена, которые нельзя выразить как `key` (невалидный UTF-8).
- `size`, `sha256` и `modified_at` снимаются с одного открытого
  дескриптора, поэтому согласованы между собой даже при параллельном `PUT`
  того же `key`.
- Хеш считается один раз: при `PUT` он запоминается в памяти вместе с
  `(dev, inode, size, mtime)` файла и переиспользуется при листинге, пока
  файл не изменился; файлы, появившиеся на диске мимо сервера, хешируются при
  первом `GET /blobs`. Кэш живёт только в процессе сервера — после
  перезапуска первый листинг прочитает все блобы заново.

Тикет 4 — удаление блоба:

- `DELETE /blobs/{key}` → `204` без тела, если блоб был и удалён; `404`
  (JSON `{"error":"not_found"}`), если под `key` нет блоба — в том числе
  если `key` указывает на каталог или лежит «под» существующим файлом.
  Повторный `DELETE` того же `key` → `404`.
- После удаления `GET /blobs/{key}` отвечает `404`, а `GET /blobs` блоб не
  показывает: список строится по файловой системе, кэш хеша для `key`
  сбрасывается. Удаляется и файл, положенный в каталог данных мимо API.
- Опустевшие родительские каталоги удаляются вместе с блобом (сам каталог
  данных и служебный `.syncbox-tmp` не трогаются). Поэтому после
  `DELETE d/e/f` ключ `d` снова свободен и `PUT /blobs/d` сохранит файл.
  Если параллельный `PUT` в тот же каталог застал его удаление между
  созданием каталога и `rename` (или внутри `mkdir -p`), `PUT` повторяет
  попытку, а не отвечает 500.

Тикет 5 — защита от directory traversal в `key`:

- Недопустимый `key` → `400`, JSON `{"error":"invalid_key","message":…}`,
  одинаково на `PUT`, `GET` и `DELETE /blobs/{key}`; на диске при этом
  ничего не создаётся, не меняется и не удаляется. Ответы на любой `key` —
  строго из списка `syncbox-openapi.yaml`, без 5xx.
- `key` — относительный POSIX-путь. Отклоняются: пустой `key`, абсолютный
  путь (`/blobs//etc/passwd`, `%2fetc`), сегменты `..` и `.` в любом месте,
  пустые сегменты (`a//b`, `a/`), NUL, невалидный UTF-8 после декодирования
  (суррогаты `%ed%a0%80`, overlong-кодировки `%c0%ae`, обрубленные
  последовательности), сегмент длиннее 255 байт, путь длиннее PATH_MAX,
  служебное имя `.syncbox-tmp`, а также `key`, который нельзя представить
  файлом (каталог на месте файла и наоборот).
- Проверка идёт по уже декодированному `key`, поэтому percent-encoded и
  смешанные формы (`%2e%2e`, `..%2f`, `a/%2e./b`) отсекаются той же
  проверкой по сегментам. Декодирование однократное: `%252e%252e` — это
  обычное имя файла `%2e%2e` внутри каталога данных. Имена, лишь похожие на
  traversal (`...`, `..a`, `a\..\b`, `~`), — обычные файлы.
- Второй слой, не зависящий от текста `key`: итоговый путь на диске после
  нормализации и разрешения символических ссылок (`realpath` самого длинного
  существующего префикса) обязан оставаться строго внутри `realpath`
  каталога данных. Symlink внутри каталога данных, ведущий наружу, даёт
  `400` на всех трёх эндпоинтах и не попадает в `GET /blobs`; symlink,
  остающийся внутри корня, допустим; сам каталог данных может быть
  символической ссылкой. Зацикленный symlink → `400`, не 500.

Тикет 6 — атомарность записи при параллельных `PUT`:

- `PUT` никогда не пишет в целевой файл напрямую: тело запроса потоково
  записывается во временный файл `<data-dir>/.syncbox-tmp/<случайное имя>.tmp`,
  данные сбрасываются на диск (`fsync`), и только затем файл одним `rename`
  переносится под `key`. Служебный каталог лежит внутри каталога данных —
  на той же файловой системе, что и целевой путь, поэтому `rename` —
  атомарная операция ядра, а не копирование между разделами. Если внутри
  каталога данных смонтирована другая файловая система, `PUT` туда
  завершится ошибкой `EXDEV` (500 с понятным сообщением в логе), а не тихим
  неатомарным копированием.
- Читатель, стартовавший в любой момент (`GET /blobs/{key}`, `GET /blobs`),
  видит либо целиком старую версию, либо целиком новую: до `rename` под
  `key` лежит прежний файл, после — новый; уже открытый на чтение файл
  дочитывается прежним содержимым до конца, даже если его успели заменить.
  Частично записанного состояния у целевого пути не бывает.
- Параллельные `PUT` по одному `key` не повреждают файл: у каждого свой
  временный файл со случайным именем, под `key` остаётся версия, чей
  `rename` был последним, и каждый ответ `201` описывает (`sha256`, `size`)
  именно своё тело. Параллельные `PUT` по разным `key` независимы.
- Временные файлы не задерживаются на диске: при успехе их забирает
  `rename`, при любой ошибке (недопустимый `key`, сбой файловой системы,
  обрыв чтения тела) их удаляет хранилище. При обрыве соединения посреди
  загрузки до хранилища дело не доходит: Puma буферизует тело целиком до
  вызова приложения и оборванный запрос отбрасывает. Файлы, оставшиеся в
  `.syncbox-tmp/` от убитого процесса (`SIGKILL` посреди записи), удаляются
  при старте сервера.
- `.syncbox-tmp` — зарезервированное имя: его содержимое не попадает в
  `GET /blobs`, а `GET`/`PUT`/`DELETE /blobs/.syncbox-tmp/...` → `400`.
- Координации между несколькими процессами сервера на одном каталоге данных
  нет — по спецификации процесс один, атомарность обеспечивает файловая
  система. Каталог после `rename` не синхронизируется: при сбое питания
  может пропасть самый последний `PUT` целиком, но не появиться
  повреждённый файл.

Тикет 7 — клиент, команда `push`:

- CLI-клиент `syncbox` (`bin/syncbox`): `syncbox push <dir> --server <url>`
  рекурсивно обходит `<dir>`, считает SHA-256 каждого файла, сравнивает со
  списком `GET /blobs` и загружает через `PUT /blobs/{key}` только те файлы,
  которых на сервере нет или чей `sha256` отличается. Файлы с совпадающим
  хешем не загружаются (даже если у них другой mtime); то, что есть на
  сервере, но нет локально, `push` не трогает и не удаляет.
- `key` — относительный POSIX-путь файла внутри `<dir>` (`docs/readme.txt`),
  та же конвенция, что на сервере; в URL сегменты percent-кодируются
  (`docs/%D1%84%D0%B0%D0%B9%D0%BB.txt`), `/` не кодируется. В обход попадают
  обычные файлы, включая dot-файлы и пустые, и symlink'и на обычные файлы
  (по содержимому цели). Symlink'и на каталоги не разворачиваются; они,
  битые ссылки, FIFO и прочие не-файлы пропускаются с предупреждением в
  stderr (`syncbox: skipping <path>: <причина>`), не ломая push. Имя файла,
  которое нельзя выразить как `key` (невалидный UTF-8), — ошибка.
- `--server <url>` обязателен (`http://` или `https://`, с хостом; хвостовой
  `/` допустим); вместо флага можно задать `SYNCBOX_SERVER`, флаг имеет
  приоритет. Флаги и позиционные аргументы — в любом порядке.
- Вывод в stdout: по строке на файл в порядке `key` —
  `uploaded <key> (<n> bytes)` либо `unchanged <key>` — и итог
  `push complete: <n> uploaded, <m> unchanged, <k> files total`.
  Файлы передаются потоково (кусками по 64 KiB) из того же открытого
  дескриптора, по которому считался хеш; ответ сервера сверяется с
  локальными `sha256`/`size`, расхождение (файл изменился во время
  загрузки) — ошибка.
- Коды возврата `syncbox`: `0` — успех; `1` — сбой (сервер недоступен,
  неожиданный ответ сервера, нечитаемый файл, каталог не найден);
  `2` — ошибка в аргументах (печатается usage). Сервер недоступен —
  сообщение `syncbox: cannot connect to server <url>: …` в stderr без
  зависания (таймауты: 10 с на соединение, 60 с на чтение/запись).
  На этом этапе первая же ошибка прерывала push; продолжение после
  частичного сбоя и отчёт по неудачным файлам добавлены в тикете 11.
- `pull`, `sync`, `status` принимаются по интерфейсу (аргументы
  разбираются так же), но отвечают
  `syncbox: <команда> is not implemented yet …` с кодом `1` — тикеты 8–10.
- Обёртка `run-client <push|pull|sync|status> <dir> --server <url>` и
  сервис `client` в `compose.yaml`: клиент исполняется в контейнере в
  сетевом пространстве хоста (`network_mode: host`), поэтому `<url>`
  означает внутри ровно то же, что снаружи, включая `http://127.0.0.1:<port>`
  сервера, поднятого `run-server`. `<dir>` монтируется как `/sync` — только
  для чтения для `push` и `status`.
- Попутно исправлена остановка сервера: штатный обработчик SIGTERM/SIGINT
  в Puma делает блокирующую остановку (join потока сервера) прямо внутри
  trap-обработчика, и на Ruby 3.3.12 с Puma 8.0.2 это примерно в 1–2 %
  случаев зависало навсегда в `IO#close` служебного pipe Puma, если сигнал
  приходил сразу после обработки запросов (воспроизводилось тестами
  клиента: 3 зависания на 150 запусков сценария «push → SIGTERM»; без
  исправления `docker compose down` в `run-server` добивал контейнер по
  таймауту). Теперь Puma работает в отдельном потоке, обработчики сигналов
  лишь кладут сигнал в очередь, а остановку выполняет главный поток из
  обычного контекста — 0 зависаний на 600 запусков того же сценария.
  Внешнее поведение не изменилось: SIGTERM/SIGINT → корректная остановка,
  код возврата `0`.

Тикет 8 — клиент, команда `pull`:

- `syncbox pull <dir> --server <url>` — зеркало `push`: берёт список
  `GET /blobs`, для каждого блоба сравнивает `sha256` с хешем локального
  файла `<dir>/<key>` и скачивает через `GET /blobs/{key}` только те, которых
  локально нет или чей хеш отличается; недостающие поддиректории создаются.
  Файлы с совпадающим хешем не скачиваются и не трогаются (mtime остаётся
  прежним). Локальные файлы, которых нет на сервере, `pull` не удаляет —
  как и `push` не удаляет лишнее на сервере.
- Запись атомарна: блоб потоково (кусками по 64 KiB) скачивается во
  временный файл `.syncbox-<hex>.tmp` в каталоге цели (та же файловая
  система → атомарный `rename`), хеш скачанного сверяется с `sha256` из
  листинга, и только затем файл одним `rename` подставляется на место.
  Расхождение хеша (блоб изменился на сервере между листингом и
  скачиванием, обрезанная передача) — ошибка, на место ничего не ложится.
  Временный файл удаляется при любом исходе, кроме убийства процесса. У
  заменяемого файла сохраняются права доступа; новые файлы получают
  `0644 & ~umask`.
- Серверу не доверяем: `key` из листинга проверяется так же строго, как
  сервер проверяет свой (не пустой, относительный, валидный UTF-8 без NUL,
  без пустых сегментов и `.`/`..`), а каталог назначения после разрешения
  символических ссылок обязан оставаться внутри `<dir>`. Иначе —
  `syncbox: refusing to pull "<key>": <причина>`, код `1`, ничего не
  записано. Symlink на обычный файл сравнивается по содержимому цели (как в
  `push`) и при расхождении заменяется обычным файлом — сам symlink, не его
  цель; битый symlink заменяется файлом. Каталог (в том числе symlink на
  каталог) на месте файла или файл на месте каталога — ошибка
  `cannot write <key>: …`, код `1`, ничего не меняется.
- Вывод в stdout: по строке на блоб в порядке `key` —
  `downloaded <key> (<n> bytes)` либо `unchanged <key>` — и итог
  `pull complete: <n> downloaded, <m> unchanged, <k> files total`.
  Коды возврата те же: `0` — успех; `1` — сбой (сервер недоступен, `404`/
  неожиданный ответ, непригодный `key`, незаписываемый каталог, нечитаемый
  локальный файл, `<dir>` не найден); `2` — ошибка в аргументах. На этом
  этапе первая же ошибка прерывала pull; продолжение после частичного
  сбоя и отчёт по неудачным файлам добавлены в тикете 11.
- `sync` и `status` по-прежнему принимаются по интерфейсу, но отвечают
  `syncbox: <команда> is not implemented yet (only push, pull are available
  in this version)` с кодом `1` — тикеты 9–10.
- `run-client pull <dir> --server <url>` монтирует `<dir>` в контейнер
  на запись (`rw`) и выполняет реальный pull; `<dir>` должен существовать.
  Файлы создаются под uid/gid вызывающего пользователя.

Тикет 9 — клиент, команда `status` (dry-run):

- `syncbox status <dir> --server <url>` сравнивает `<dir>` со списком
  `GET /blobs` по `key` (относительный POSIX-путь внутри `<dir>`, та же
  конвенция, что в `push`/`pull`) и SHA-256 и печатает, что сделали бы
  `push` и `pull`, ничего не меняя. Это единственный запрос к серверу:
  в листинге уже есть `sha256`, тела блобов не скачиваются. Ни одного
  `PUT`/`DELETE`, ни одного созданного, изменённого или удалённого
  локального файла (mtime тоже не трогаются); `run-client` монтирует
  `<dir>` только для чтения.
- Вывод в stdout: по строке на `key` в порядке `key`, первое слово —
  направление:
  - `upload    <key> (<n> bytes; only local, not on server)` — есть
    локально, нет на сервере: `push` загрузил бы;
  - `download  <key> (<n> bytes; only on server, not local)` — есть на
    сервере, нет локально: `pull` скачал бы;
  - `differs   <key> (local <n> bytes, server <m> bytes; push would upload,
    pull would download)` — есть с обеих сторон, SHA-256 отличается:
    `push` загрузил бы локальную версию, `pull` скачал бы серверную (кто
    победит при `sync` — тикет 10);
  - `unchanged <key>` — хеши совпадают (mtime не учитывается).

  Итог: `status: <a> to upload (<b> only local), <c> to download (<d> only
  on server), <e> differing on both sides, <f> unchanged, <k> files total
  (dry run, nothing changed)`, где `a = b + e`, `c = d + e`,
  `k = b + d + e + f`. Если расхождений нет — `status: in sync, <f>
  unchanged, nothing to upload or download (dry run, nothing changed)`.
- Код возврата `0`, когда сравнение выполнено, есть расхождения или нет:
  `status` их показывает, а не исправляет. `1` — сбой (сервер недоступен,
  неожиданный ответ или битая запись в листинге, нечитаемый локальный
  файл, `<dir>` не найден); `2` — ошибка в аргументах. Локальный каталог
  обходится до первого обращения к сети; не-файлы и битые symlink'и
  пропускаются с предупреждением в stderr, как в `push`; symlink на файл
  сравнивается по содержимому цели.
- `sync` на этом этапе ещё принимался только по интерфейсу
  (`syncbox: sync is not implemented yet …`, код `1`) — реализован в
  тикете 10.
- `run-client status <dir> --server <url>` (или `SYNCBOX_SERVER`)
  выполняет реальный status; `<dir>` монтируется в контейнер только для
  чтения (`ro`), так что контейнер физически не может ничего в нём
  изменить.

Тикет 10 — клиент, команда `sync`:

- `syncbox sync <dir> --server <url>` — двунаправленная синхронизация,
  push и pull в один проход. По каждому `key` из объединения локальных
  файлов и листинга `GET /blobs` (сравнение по SHA-256):
  - есть только локально → `PUT` на сервер (как `push`);
  - есть только на сервере → `GET` и запись в `<dir>` с созданием
    поддиректорий (как `pull`: временный файл рядом с целью, сверка хеша с
    листингом, атомарный `rename`, та же проверка `key` против traversal);
  - хеши совпадают → ничего (`unchanged`);
  - хеши отличаются и относительно последнего известного общего состояния
    изменилась одна сторона → переносится её версия (`changed locally` →
    upload, `changed on server` → download); mtime при этом не
    учитывается;
  - хеши отличаются и изменились обе стороны — конфликт, правило
    спецификации: побеждает версия с более свежим временем (локальный
    mtime из ФС против `modified_at` из листинга сервера), при равенстве —
    локальная. Победившая локальная версия загружается на сервер,
    победившая серверная — скачивается поверх локальной. Времена
    сравниваются с той точностью, с какой сервер отдаёт `modified_at`
    (целые секунды): локальный mtime округляется вниз до неё, иначе доли
    секунды, которые сервер отбросил, выглядели бы как «локальная новее».
- Последнее известное общее состояние — манифест
  `<dir>/.syncbox/state.json`: `{"version":1,"files":{"<key>":{"sha256":
  "…"}}}` — по каждому `key` хеш содержимого, которое после прошлого sync
  лежало на обеих сторонах. Записывается атомарно (временный файл в
  `.syncbox/` и `rename`) в конце sync, если изменился; при сбое посреди
  прохода — для уже перенесённых файлов, чтобы следующий sync не принял
  доделанную часть за конфликт. Ключи, исчезнувшие с обеих сторон, из
  манифеста уходят. Повреждённый манифест — ошибка с путём и
  предложением удалить его (`sync state … is corrupt (…); delete it to
  start over`), код `1`.
- Первый запуск (манифеста нет): файлы с одной стороны просто переносятся,
  а файл, который есть с обеих сторон с разным содержимым, разрешается по
  тому же правилу mtime (в выводе — `conflict, never synced before`):
  без общего состояния нельзя доказать, что менялась только одна сторона.
- Имя `.syncbox` в корне `<dir>` зарезервировано клиентом: `push`,
  `status` и `sync` не считают его содержимое файлами `<dir>` (манифест не
  уезжает на сервер), а блобы сервера с первым сегментом `key` `.syncbox`
  пропускаются в `pull`, `status` и `sync` с предупреждением
  `syncbox: skipping <key>: .syncbox/ is reserved for the client's sync
  state` — сервер не может подменить состояние клиента. Вложенные
  `sub/.syncbox/...` — обычные файлы.
- `sync` ничего не удаляет ни локально, ни на сервере: файл, удалённый с
  одной стороны после прошлого sync, снова переносится с другой (как
  `push`/`pull` не трогают лишнее на другой стороне). Распространение
  удалений спецификацией не предусмотрено.
- Вывод в stdout, по строке на `key` в порядке `key`:
  `uploaded <key> (<n> bytes; <причина>)`, `downloaded <key> (<n> bytes;
  <причина>)`, `unchanged <key>`, где причина — `only local`, `only on
  server`, `changed locally`, `changed on server`, `conflict: local <t>
  is newer than server <t>`, `conflict: server <t> is newer than local
  <t>`, `conflict: same mtime <t>, local wins` (на первом запуске —
  `conflict, never synced before: …`). Итог: `sync complete: <u>
  uploaded, <d> downloaded, <x> unchanged, <k> files total, <c> conflicts
  resolved`.
- Коды возврата: `0` — синхронизация выполнена; `1` — сбой (сервер
  недоступен, неожиданный ответ или битая запись в листинге, `modified_at`
  отсутствует или не разбирается у конфликтного файла, непригодный `key`,
  нечитаемый или незаписываемый файл, повреждённый манифест, `<dir>` не
  найден); `2` — ошибка в аргументах. Обход каталога и чтение манифеста —
  до первого обращения к сети. На этом этапе первая же ошибка прерывала
  sync; продолжение после частичного сбоя и отчёт по неудачным файлам
  добавлены в тикете 11.
- `run-client sync <dir> --server <url>` (или `SYNCBOX_SERVER`) выполняет
  реальный sync; `<dir>` монтируется в контейнер на запись (`rw`), файлы и
  манифест создаются под uid/gid вызывающего пользователя.

Тикет 11 — обработка сетевых ошибок и частичных сбоев на клиенте
(раздел «Коды возврата и ошибки» спецификации):

- Недоступность сервера. Все команды (`push`, `pull`, `sync`, `status`)
  при невозможности соединиться — имя не резолвится, соединение
  отклонено, нет маршрута, таймаут соединения — печатают в stderr
  `syncbox: cannot connect to server <url>: <причина>` (причина — от ОС
  или резолвера: `Connection refused - connect(2) for "127.0.0.1" port
  8080`, `getaddrinfo: Name or service not known`, `connection timed out
  after 10s`) и завершаются с кодом `1`, ничего не напечатав в stdout и
  ничего не изменив. Сервер, который принял соединение, но не отвечает, —
  `syncbox: GET /blobs: request to <url> failed: server did not respond
  within 60s (read timeout)`, код `1`; сервер, оборвавший соединение, —
  `… failed: server closed the connection without a complete response`.
  Зависания нет: на все сетевые операции стоят явные таймауты — 10 с на
  соединение (включая разрешение имени), 60 с на ожидание ответа, 60 с на
  отправку данных. Флагов для таймаутов нет (спецификация их не
  предусматривает), как нет и повторов: автоматический повтор
  идемпотентных запросов в Net::HTTP выключен, сбой запроса виден сразу.
- Частичный сбой. Если при обработке множества файлов падает один —
  сервер ответил не тем кодом (5xx, 4xx, 404 на только что перечисленный
  блоб), оборвал соединение или не ответил в срок на конкретный запрос,
  хеш скачанного разошёлся с листингом, локальный файл нечитаем или цель
  незаписываема, `key` с сервера непригоден, `modified_at` конфликтного
  файла не разбирается — команда не прерывается: для него в stdout
  печатается `failed <key>` (у `status` — `failed    <key> (not compared,
  see stderr)`), в stderr сразу — `syncbox: failed <key>: <причина>`, а
  остальные файлы обрабатываются до конца. Итоговая строка в stdout —
  `push incomplete: <n> uploaded, <m> unchanged, <f> failed, <k> files
  total` (так же `pull incomplete: …`, `sync incomplete: … <f> failed, …`,
  `status: <f> failed (not compared), …`), а в stderr — сводный отчёт по
  неудачным файлам:

  ```
  syncbox: push failed for 1 of 3 files:
    docs/b.txt: PUT /blobs/docs/b.txt: server responded 500: disk on fire
  ```

  Код возврата `1`, даже если остальные файлы перенесены. После сбоя
  запроса клиент соединяется с сервером заново для следующего файла; если
  соединиться уже нельзя (сервер умер посреди работы) — это недоступность
  сервера: команда прерывается с `cannot connect to server …`, уже
  перенесённое остаётся перенесённым. В `sync` упавший `key` не попадает в
  манифест общего состояния (прежняя запись для него сохраняется),
  поэтому следующий sync решает его заново; конфликт считается
  разрешённым только после успешного переноса. При неудачном скачивании
  локальная версия не трогается: временный файл удаляется, на место
  ничего не ложится. Для `status` единственный запрос к серверу —
  листинг, поэтому частичный сбой у него — только нечитаемый локальный
  файл.
- Что по-прежнему прерывает команду сразу (код `1`): сервер недоступен,
  не удалось получить или разобрать листинг `GET /blobs` (без него
  сравнивать не с чем), `<dir>` не найден, ошибка обхода каталога
  (невалидное UTF-8 имя, недоступный подкаталог), повреждённый манифест
  sync. Код `2` — ошибка в аргументах. Спецификация не разграничивает
  коды для разных сбоев, поэтому любой сбой — `1`; что именно случилось,
  видно по сообщению в stderr.
- Успешные пути не изменились: вывод и код `0` при полном успехе те же,
  что в тикетах 7–10.

Стартовый бэклог спецификации (тикеты 1–11) закрыт.

## Запуск

```sh
./run-server --data-dir ./data --port 8080
# или
SYNCBOX_DATA_DIR=./data SYNCBOX_PORT=8080 ./run-server

curl -i http://127.0.0.1:8080/healthz

# загрузить файл под ключом docs/readme.txt (каталог docs создастся сам)
curl -i -X PUT --data-binary @README.md http://127.0.0.1:8080/blobs/docs/readme.txt
# → 201 {"key":"docs/readme.txt","sha256":"…","size":…}

# скачать его обратно; 404, если такого ключа нет
curl -s http://127.0.0.1:8080/blobs/docs/readme.txt -o readme.copy

# список всех блобов с метаданными (пустое хранилище → [])
curl -s http://127.0.0.1:8080/blobs
# → [{"key":"docs/readme.txt","size":7340,"sha256":"…","modified_at":"2026-10-05T22:38:46Z"}]

# удалить блоб: 204 без тела; повторно или для несуществующего ключа — 404
curl -i -X DELETE http://127.0.0.1:8080/blobs/docs/readme.txt

# directory traversal (в любой форме) — 400 на PUT/GET/DELETE, на диске ничего не меняется
curl -i --path-as-is -X PUT --data-binary x http://127.0.0.1:8080/blobs/../etc/passwd
# → 400 {"error":"invalid_key","message":"key must not contain '.' or '..' segments"}
```

`run-server` работает в текущем процессе (без демонизации); Ctrl-C или
SIGTERM корректно останавливают сервер и удаляют контейнер. Каталог данных —
путь на хосте: обёртка создаёт его при отсутствии и монтирует в контейнер как
`/data`. Контейнер запускается под uid/gid вызывающего пользователя, поэтому
файлы в каталоге данных не достаются `root`'у.

Каждый запуск живёт в отдельном compose-проекте `syncbox-<port>`, так что
несколько серверов на разных портах не мешают друг другу.

Клиент — через обёртку `run-client` (тоже в контейнере):

```sh
# загрузить на сервер всё из ./my-folder, чего там нет или что отличается по SHA-256
./run-client push ./my-folder --server http://127.0.0.1:8080
# → uploaded docs/readme.txt (7340 bytes)
#   unchanged a.txt
#   push complete: 1 uploaded, 1 unchanged, 2 files total

# адрес сервера можно задать переменной окружения
SYNCBOX_SERVER=http://127.0.0.1:8080 ./run-client push ./my-folder

# скачать в ./other-folder всё, чего там нет или что отличается по SHA-256
# (лишние локальные файлы остаются на месте)
./run-client pull ./other-folder --server http://127.0.0.1:8080
# → downloaded docs/readme.txt (7340 bytes)
#   unchanged a.txt
#   pull complete: 1 downloaded, 1 unchanged, 2 files total

# dry-run: что сделали бы push и pull для ./my-folder, ничего не меняя
./run-client status ./my-folder --server http://127.0.0.1:8080
# → differs   a.txt (local 9 bytes, server 6 bytes; push would upload, pull would download)
#   upload    docs/new.txt (9 bytes; only local, not on server)
#   unchanged docs/readme.txt
#   download  srv/only.txt (11 bytes; only on server, not local)
#   status: 2 to upload (1 only local), 2 to download (1 only on server), 1 differing on both sides, 1 unchanged, 4 files total (dry run, nothing changed)
# код возврата 0 и при расхождениях; если их нет:
# → status: in sync, 2 unchanged, nothing to upload or download (dry run, nothing changed)

# двунаправленная синхронизация: push и pull в один проход, конфликты — по mtime
./run-client sync ./my-folder --server http://127.0.0.1:8080
# → uploaded docs/new.txt (9 bytes; only local)
#   unchanged docs/readme.txt
#   downloaded srv/only.txt (11 bytes; only on server)
#   uploaded a.txt (9 bytes; conflict: local 2026-10-06T03:33:40Z is newer than server 2026-10-06T02:33:39Z)
#   sync complete: 2 uploaded, 1 downloaded, 1 unchanged, 4 files total, 1 conflicts resolved
# последнее общее состояние запоминается в ./my-folder/.syncbox/state.json;
# повторный sync без изменений ничего не переносит:
# → unchanged a.txt
#   …
#   sync complete: 0 uploaded, 0 downloaded, 4 unchanged, 4 files total, 0 conflicts resolved

# сервер недоступен: причина в stderr, код возврата 1, без зависания (таймауты 10 с / 60 с)
./run-client status ./my-folder --server http://127.0.0.1:9999
# → syncbox: cannot connect to server http://127.0.0.1:9999: Connection refused - connect(2) for "127.0.0.1" port 9999

# частичный сбой: остальные файлы переносятся, в конце — отчёт по упавшим в stderr, код возврата 1
./run-client push ./my-folder --server http://127.0.0.1:8080
# → uploaded a.txt (9 bytes)
#   failed docs/b.txt
#   uploaded docs/c.txt (3 bytes)
#   push incomplete: 2 uploaded, 0 unchanged, 1 failed, 3 files total
# stderr:
#   syncbox: failed docs/b.txt: PUT /blobs/docs/b.txt: server responded 500: disk on fire
#   syncbox: push failed for 1 of 3 files:
#     docs/b.txt: PUT /blobs/docs/b.txt: server responded 500: disk on fire
```

`run-client` собирает образ, монтирует `<dir>` в контейнер клиента как
`/sync` (для `push` и `status` — только для чтения, для `pull` и `sync` —
на запись), а подкоманду и остальные аргументы форвардит `bin/syncbox`. Контейнер клиента работает в
сетевом пространстве хоста, так что `--server` указывает тот же адрес, что и
для `curl` с хоста. Каждый вызов живёт в своём compose-проекте и убирает за
собой контейнер; Ctrl-C останавливает клиент. Код возврата `run-client` —
код клиента (`0` успех, `1` сбой, `2` ошибка в аргументах; `1` и если
`<dir>` не существует). В stdout — только вывод клиента; сообщения Docker и
compose идут в stderr.

## Тесты

```sh
./run-tests
```

Собирает образ и прогоняет все тесты (minitest) в контейнере; код возврата
ненулевой, если хоть один тест упал. Интеграционные тесты запускают
настоящий `bin/syncbox-server` отдельным процессом и ходят в него по HTTP —
в том числе тесты клиента: `push`, `pull`, `status` и `sync` гоняются против живого сервера
как через `Syncbox::Client::CLI` в процессе, так и через `bin/syncbox`
отдельным процессом (коды возврата, вывод, `SYNCBOX_SERVER`). Для `sync`
покрыты все ветви решения: только-локальный и только-серверный файл,
изменение с одной стороны (включая случай, когда mtime говорит обратное —
он не учитывается), конфликт с более свежей локальной и с более свежей
серверной версией, равный mtime и разница в доли секунды (локальная
побеждает), первый запуск без манифеста, отсутствие удалений, повторный
запуск без изменений (ни файлы, ни манифест не трогаются), сохранение
манифеста для перенесённых файлов при сбое, повреждённый манифест,
невидимость `.syncbox` для `push`/`status`/`sync` и пропуск таких блобов с
сервера. Поведение
`pull` и `sync` на недоверенных ответах сервера (traversal в `key`, расхождение хеша
листинга и тела, `404` на только что перечисленный блоб, битый или
отсутствующий `modified_at`, доли секунды в `modified_at`) проверяется против
поддельного HTTP-сервера на `TCPServer` (`TestSupport::FakeServer`); тот же
сервер подтверждает, что `status` шлёт серверу один `GET /blobs` и ничего
больше, а снимки локального каталога и каталога данных сервера до и после
`status` — что он ничего не меняет. Сетевые ошибки и частичные сбои
(`test/client_failures_test.rb`) гоняются для всех четырёх команд: соединение
отклонено, имя не резолвится, таймаут соединения (немаршрутизируемый адрес),
сервер принимает соединение и молчит (таймаут ответа), сервер обрывает
соединение — везде проверяются сообщение с причиной, код `1` и время
выполнения (нет зависания; таймауты для тестов укорачиваются подменой
`Api.timeouts`). Частичные сбои: 5xx/4xx, обрыв и таймаут на конкретный
`key` при `push`, `pull` и `sync`, нечитаемый локальный файл и незаписываемая
цель, смерть сервера посреди `push`, сохранение прежнего общего состояния
для упавшего `key` в `sync` — везде остальные файлы перенесены, отчёт в
stderr, код `1`; для этого `FakeServer` умеет отвечать по телу запроса
(`put_ok`), обрывать соединение (`:drop`), молчать (`:hang`) и переставать
принимать соединения. Тестовый сервер
останавливается SIGTERM'ом; если он не завершился за 10 с, хелпер печатает
его лог в stderr и убивает процесс, чтобы зависание сервера не подвешивало
весь прогон.

```
lib/syncbox/client/cli.rb         клиент: диспетчер команд, коды возврата
test/                             minitest: юнит-тесты и интеграционные тесты
Dockerfile, compose.yaml          сборка образа, сервисы `server`, `client` и `test`
run-server, run-client, run-tests обёртки, вызывающие только `docker compose`
```

Клиент (`bin/syncbox`) использует только стандартную библиотеку Ruby
(`net/http`, `digest`, `optparse`) и не загружает серверные зависимости.

Коды возврата `bin/syncbox-server`: `0` — штатное завершение, `1` — не
удалось подготовить каталог данных, `2` — ошибка в аргументах (usage).

Внутри контейнера сервер слушает `0.0.0.0:<port>`; снаружи порт доступен
через публикацию `<port>:<port>` в `compose.yaml`.

Зависимости: [puma](https://github.com/puma/puma) (HTTP-сервер),
[rack](https://github.com/rack/rack); для тестов — minitest и rack-test.
Версии зафиксированы в `Gemfile.lock`, образ собирается с
`BUNDLE_FROZEN=1`. Чтобы обновить зависимости, поменяйте `Gemfile` и
перегенерируйте lock внутри контейнера, например:

```sh
docker compose run --rm -T test bundle lock --print > Gemfile.lock
```
