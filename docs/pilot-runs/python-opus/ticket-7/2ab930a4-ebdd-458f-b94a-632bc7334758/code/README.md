# Syncbox (Python)

Самостоятельно хостящееся файловое хранилище с синхронизацией. Контракт —
[SYNCBOX-SPEC.md](SYNCBOX-SPEC.md) и [syncbox-openapi.yaml](syncbox-openapi.yaml).

Всё исполняется в Docker через `docker compose` ([compose.yaml](compose.yaml));
на хосте нужны только Docker с плагином compose и bash.

## Запуск

```sh
./run-server --data-dir ./data --port 8080   # или SYNCBOX_DATA_DIR / SYNCBOX_PORT
./run-client push ./dir --server http://127.0.0.1:8080   # или SYNCBOX_SERVER
./run-tests                                  # все тесты; аргументы уходят в pytest
```

`run-server` работает на переднем плане, останавливается по SIGTERM/SIGINT
(контейнер при этом удаляется). Каталог данных создаётся, если его нет,
и монтируется в контейнер; файлы пишутся от имени вызывающего пользователя.
Порт публикуется на `127.0.0.1`; другой адрес — через `SYNCBOX_PUBLISH_ADDR`
(например `0.0.0.0`).

`run-client <push|pull|sync|status> <dir> --server <url>` запускает клиент
`syncbox` в контейнере: `<dir>` монтируется в него (только на чтение — пока
есть лишь `push`), остальные аргументы передаются клиенту как есть.
Контейнер работает в сетевом пространстве хоста, поэтому `<url>` значит то
же, что и на хосте. Вывод клиента — в stdout, ошибки и предупреждения — в
stderr. По SIGTERM/SIGINT контейнер останавливается и удаляется.

## Клиент

- `push` обходит `<dir>` рекурсивно, считает SHA-256 каждого файла,
  сравнивает со списком `GET /blobs` и загружает (`PUT`) файлы, которых на
  сервере нет или у которых другой SHA-256. Ключ — относительный POSIX-путь
  (`docs/readme.txt`). Совпадающие по содержимому файлы не загружаются;
  блобы, которых нет локально, не трогаются. Печатает `added <key>` /
  `updated <key>` и итог `N uploaded, M already up to date`.
- Синхронизируются только обычные файлы: символические ссылки (на файлы и
  каталоги) и специальные файлы пропускаются с предупреждением.
- Загрузка проверяется: `sha256` из ответа сервера должен совпасть с хешем
  отправленных байтов. Если размер файла изменился во время отправки,
  запрос обрывается до конца тела, и сервер сохраняет прежнюю версию.
- Коды возврата: `0` — успех, `1` — команда не выполнена (сервер недоступен,
  ошибка ответа, нечитаемый файл, имя не в UTF-8), `2` — ошибка
  использования (нет `--server`, неверный URL, неверные аргументы). Пока
  push останавливается на первой ошибке; таймауты — 10 с на соединение,
  120 с ожидания данных.
- `pull`, `sync`, `status` принимают те же аргументы, но пока не
  реализованы: сообщение в stderr, код `1`.

## Устройство

- `syncbox/server/` — HTTP-сервер на стандартной библиотеке
  (`http.server.ThreadingHTTPServer`), без внешних зависимостей.
  Точка входа: `python -m syncbox.server --data-dir PATH [--port N]`.
- Каталог данных: `blobs/<key>` — блобы, `tmp/` — загрузки в процессе.
  Блоб пишется во временный файл в `tmp/` и атомарно переименовывается
  поверх `blobs/<key>`, поэтому читатель видит либо старую версию, либо
  новую целиком. `tmp/` и `blobs/` должны быть на одной файловой системе
  (сервер проверяет это при старте); остатки в `tmp/` от упавшего сервера
  удаляются при старте.
- `syncbox/client/` — клиент, тоже только стандартная библиотека
  (`http.client`, keep-alive-соединение): `cli.py` — аргументы и коды
  возврата, `api.py` — HTTP, `local.py` — обход каталога и хеши,
  `push.py` — сравнение и загрузка. Исполняемый файл — `bin/syncbox`
  (в образе — `/usr/local/bin/syncbox`); также `python -m syncbox.client`.
- `tests/` — pytest: конфигурация, HTTP-слой in-process, сервер как
  реальный процесс, клиент против in-process сервера и `syncbox` как
  процесс.
- `Dockerfile` — стадии `runtime` (сервер), `client` (клиент) и `test`
  (клиент + pytest и тесты).
