# Syncbox (Python)

Самостоятельно хостящееся файловое хранилище с синхронизацией. Контракт —
[SYNCBOX-SPEC.md](SYNCBOX-SPEC.md) и [syncbox-openapi.yaml](syncbox-openapi.yaml).

Всё исполняется в Docker через `docker compose` ([compose.yaml](compose.yaml));
на хосте нужны только Docker с плагином compose и bash.

## Запуск

```sh
./run-server --data-dir ./data --port 8080   # или SYNCBOX_DATA_DIR / SYNCBOX_PORT
./run-client push ./dir --server http://127.0.0.1:8080   # или SYNCBOX_SERVER
./run-client pull ./dir --server http://127.0.0.1:8080
./run-client sync ./dir --server http://127.0.0.1:8080
./run-client status ./dir --server http://127.0.0.1:8080
./run-tests                                  # все тесты; аргументы уходят в pytest
```

`run-server` работает на переднем плане, останавливается по SIGTERM/SIGINT
(контейнер при этом удаляется). Каталог данных создаётся, если его нет,
и монтируется в контейнер; файлы пишутся от имени вызывающего пользователя.
Порт публикуется на `127.0.0.1`; другой адрес — через `SYNCBOX_PUBLISH_ADDR`
(например `0.0.0.0`).

`run-client <push|pull|sync|status> <dir> --server <url>` запускает клиент
`syncbox` в контейнере: `<dir>` монтируется в него (на запись: туда пишут
`pull` и `sync`, от имени вызывающего пользователя; для `status` — только на
чтение), остальные аргументы передаются клиенту как есть. Для `sync`
дополнительно монтируется каталог состояния синхронизации (см. ниже) —
`SYNCBOX_STATE_DIR`, иначе `$XDG_STATE_HOME/syncbox`, иначе
`~/.local/state/syncbox`; `run-client` создаёт его, если нужно.
Контейнер работает в сетевом пространстве хоста, поэтому `<url>` значит то
же, что и на хосте. Вывод клиента — в stdout, ошибки и предупреждения — в
stderr. По SIGTERM/SIGINT контейнер останавливается и удаляется.

## Клиент

- `push` обходит `<dir>` рекурсивно, считает SHA-256 каждого файла,
  сравнивает со списком `GET /blobs` и загружает (`PUT`) файлы, которых на
  сервере нет или у которых другой SHA-256. Ключ — относительный POSIX-путь
  (`docs/readme.txt`). Совпадающие по содержимому файлы не загружаются;
  блобы, которых нет локально, не трогаются. Печатает `added <key>` /
  `updated <key>` и итог `N uploaded, M already up to date`.
- `pull` — обратное: по списку `GET /blobs` скачивает (`GET /blobs/{key}`)
  блобы, которых нет в `<dir>` или чей SHA-256 отличается от локального
  файла, и пишет их по пути `<dir>/<key>`, создавая недостающие каталоги.
  Совпадающие по содержимому файлы не скачиваются; локальные файлы, которых
  нет на сервере, не трогаются. Печатает `added <key>` / `updated <key>` и
  итог `N downloaded, M already up to date`.
- `status` — dry-run: сравнивает `<dir>` со списком `GET /blobs` так же, как
  `push` и `pull` (по ключу и SHA-256), и печатает, что они передали бы,
  ничего не меняя: к серверу уходит только `GET /blobs`, локальные файлы
  только читаются. Строка на файл — направление, вид и ключ:

  ```
  upload    new      docs/new.txt       # есть локально, нет на сервере
  upload    changed  notes.txt          # на сервере другая версия
  download  changed  notes.txt          # то же с другой стороны
  download  new      remote/only.txt    # есть на сервере, нет локально
  2 to upload, 2 to download, 5 up to date
  ```

  Файл с разным содержимым на двух сторонах попадает в оба направления:
  `push` загрузил бы локальную версию, `pull` скачал бы серверную (какую
  выберет `sync`, решает правило разрешения конфликтов — оно не часть
  `status`). Если расхождений нет — `nothing to upload or download, N up to
  date`. Код возврата `0` независимо от наличия расхождений.
- `sync` — `push` и `pull` за один проход: файлы сопоставляются по ключу и
  сравниваются по SHA-256 так же. Для файла, который различается:
  - есть только на одной стороне — переносится на другую (загружается или
    скачивается);
  - есть на обеих, и одна сторона не менялась с последней синхронизации
    (её SHA-256 совпадает с записанным в состоянии) — переносится версия
    другой стороны;
  - есть на обеих, и изменились обе (**конфликт**) — побеждает более свежая
    версия: mtime локального файла против `modified_at` блоба из
    `GET /blobs` (сравнение с точностью до микросекунды, как отдаёт
    сервер); при равенстве — локальная;
  - есть на обеих, а общего состояния для файла нет (первая синхронизация
    или файл создан на обеих сторонах независимо) — ни одна сторона не
    известна как неизменная, решает то же правило по времени.

  `sync` ничего не удаляет: файл, удалённый на одной стороне, возвращается
  с другой. Строка на перенесённый файл — направление, вид, ключ и
  пояснение для решений по времени:

  ```
  upload    new       docs/new.txt
  download  changed   notes.txt
  upload    conflict  report.txt  (local is newer)
  download  differs   draft.txt  (no common version known; server is newer)
  2 uploaded, 2 downloaded, 5 already up to date (1 conflict resolved)
  ```

  Скачивание — как в `pull`; если локальный файл изменился между подсчётом
  хеша и заменой, он не перезаписывается, а пропускается с предупреждением.
- Состояние синхронизации — SHA-256 файлов, совпадавших на обеих сторонах
  по итогам прошлого `sync` («последнее известное общее состояние»). Хранится
  вне `<dir>` (ничего лишнего не попадает ни в каталог, ни на сервер), по
  JSON-файлу на пару «каталог + сервер» в `SYNCBOX_STATE_DIR`, иначе
  `$XDG_STATE_HOME/syncbox`, иначе `~/.local/state/syncbox`. Каталог
  определяется реальным путём или `SYNCBOX_DIR_ID` (его выставляет
  `run-client` — путь на хосте, так как в контейнере каталог всегда
  `/work`). Состояние пишется атомарно и после частичного сбоя тоже (для
  уже синхронизированных файлов). Потеря или порча состояния не ломает
  `sync`: оно считается пустым (с предупреждением), и расхождения решаются
  правилом по времени; ошибка записи — предупреждение, не ошибка.
- Синхронизируются только обычные файлы: символические ссылки (на файлы и
  каталоги) и специальные файлы пропускаются с предупреждением — и при
  обходе `<dir>` в `push`/`sync`, и на пути к файлу в `pull`/`sync`
  (запись никогда не идёт через ссылку). Сам `<dir>` может быть ссылкой.
- Загрузка проверяется: `sha256` из ответа сервера должен совпасть с хешем
  отправленных байтов. Если размер файла изменился во время отправки,
  запрос обрывается до конца тела, и сервер сохраняет прежнюю версию.
- Скачивание тоже: размер и SHA-256 полученных байтов должны совпасть со
  списком. Файл пишется во временный `.syncbox-*.tmp` в том же каталоге и
  атомарно переименовывается поверх старого (права старого файла
  сохраняются), так что локальный файл — либо прежний, либо новый целиком.
  Ключи от сервера не доверенные: блоб с ключом, где есть `..`, `.`, пустой
  или абсолютный компонент, не скачивается и считается сбоем по этому файлу
  (в `pull` и `sync`; остальные файлы обрабатываются). Блоб, удалённый на
  сервере между списком и скачиванием, пропускается с предупреждением.
- Ошибки и коды возврата: `0` — успех, `1` — команда не выполнена (целиком
  или по части файлов, см. ниже), `2` — ошибка использования (нет
  `--server`, неверный URL, неверные аргументы).
  - **Сервер недоступен** — соединение отклонено, имя не резолвится, таймаут
    соединения или ответа, — либо не отдал список блобов: команда сразу
    завершается с кодом `1` и сообщением о причине в stderr, например
    `syncbox: error: cannot reach server http://127.0.0.1:8080: Connection refused`
    или `syncbox: error: timed out: no response from server http://… within 60 s`.
    Таймауты явные: 10 с на резолв имени и соединение, 60 с тишины на открытом
    соединении (ожидание ответа, приём и отправка данных). То же, если не
    читается сам `<dir>`.
  - **Частичный сбой** — не удалось обработать отдельный файл: запрос по нему
    оборвался или истёк по таймауту, сервер ответил ошибкой (например `5xx`),
    локальный файл или каталог не читается / не записывается, имя не в UTF-8,
    недопустимый ключ от сервера. Ошибка сразу печатается в stderr, остальные
    файлы обрабатываются до конца; к итоговой строке в stdout добавляется
    `, N failed`, а в конце stderr — сводный отчёт, код возврата `1`:

    ```
    syncbox: error: 2 files failed:
      cannot upload 'bad.txt': HTTP 500 Internal Server Error: disk on fire
      cannot read 'secret': Permission denied
    ```

    Если по ходу работы сервер перестал принимать соединения, остальные
    передачи не ждут каждая своего таймаута, а сразу попадают в отчёт как
    `not attempted, the server is unreachable` (причина — в заголовке отчёта).
    `sync` не трогает ни с какой стороны файл, который не удалось прочитать
    локально (и всё под нечитаемым каталогом): что там лежит — неизвестно, и
    отсутствующим он не считается; `status` по той же причине не включает его
    в вывод. Состояние `sync` записывается только для файлов, которые
    совпали или были перенесены, так что следующий `sync` доделает остальное.
    Предупреждения (пропущенные ссылки и спецфайлы, файл, изменённый во время
    `sync`, блоб, удалённый с сервера) сбоями не считаются.

## Устройство

- `syncbox/server/` — HTTP-сервер на стандартной библиотеке
  (`http.server.ThreadingHTTPServer`), без внешних зависимостей.
  Точка входа: `python -m syncbox.server --data-dir PATH [--port N]`.
- Каталог данных: `blobs/<key>` — блобы, `tmp/` — загрузки в процессе.
  Блоб пишется во временный файл в `tmp/` и атомарно переименовывается
  поверх `blobs/<key>`, поэтому читатель видит либо старую версию, либо
  новую целиком. `tmp/` и `blobs/` должны быть на одной файловой системе
  (сервер проверяет это при старте); остатки в `tmp/` от упавшего сервера
  удаляются при старте.
- `syncbox/client/` — клиент, тоже только стандартная библиотека
  (`http.client`, keep-alive-соединение): `cli.py` — аргументы и коды
  возврата, `api.py` — HTTP, `local.py` — обход каталога и хеши,
  `push.py` / `pull.py` — сравнение и загрузка / скачивание, `status.py` —
  сравнение без передачи, `sync.py` — двунаправленная синхронизация,
  `state.py` — её состояние между запусками, `errors.py` — ошибки и сбор
  сбоев по отдельным файлам для итогового отчёта. Исполняемый
  файл — `bin/syncbox` (в образе — `/usr/local/bin/syncbox`); также
  `python -m syncbox.client`.
- `tests/` — pytest: конфигурация, HTTP-слой in-process, сервер как
  реальный процесс, клиент против in-process сервера и `syncbox` как
  процесс.
- `Dockerfile` — стадии `runtime` (сервер), `client` (клиент) и `test`
  (клиент + pytest и тесты).
