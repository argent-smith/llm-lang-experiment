Продолжаем проект Syncbox (тикеты 1-5 — каркас сервера, happy path для PUT/GET блоба, список блобов, удаление блоба, защита от directory traversal — уже сделаны в этом же репозитории). Тикет 6: атомарность записи при параллельных PUT.

Полная спецификация — в файлах SYNCBOX-SPEC.md и syncbox-openapi.yaml в корне этого репозитория — прочитай перед началом, если нужно освежить детали.

Нужно реализовать:

- Запись блоба на диск должна быть атомарной: запись во временный файл (в той же файловой системе, что и целевой путь, чтобы rename был атомарной операцией, а не копированием между разными разделами) и последующий rename в целевой путь — не запись напрямую в целевой файл.
- Параллельные PUT по одному и тому же ключу не должны приводить к повреждённому файлу — читатель (GET), стартовавший в любой момент, должен видеть либо полностью старое содержимое, либо полностью новое, никогда не частично записанное.
- Параллельные PUT по разным ключам не должны мешать друг другу.
- Временные файлы не должны оставаться на диске после завершения запроса (ни при успехе, ни при ошибке/обрыве соединения) и не должны попадать в GET /blobs (список) или быть доступны через GET /blobs/{key}.

Границы этого тикета:

- Клиентские команды (push/pull/status/sync) — отдельные будущие тикеты, не входят.
- Блокировки на уровне приложения (mutex/lock file) для координации между несколькими процессами сервера — не требуются; спецификация не подразумевает несколько процессов сервера, атомарность обеспечивается на уровне файловой системы (rename), не координацией между процессами.

Не реализовывай перечисленное выше заранее — не входит в объём этого тикета.

Сервер по-прежнему должен исполняться в Docker-контейнере через docker compose — не переделывай эту часть, если она уже работает, расширяй по необходимости.

Библиотеки и внутреннее устройство — на твоё усмотрение, как и в предыдущих тикетах.
