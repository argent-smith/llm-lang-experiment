Проверь текущую реализацию сервера Syncbox (тикеты 1-7 уже сделаны в этом же репозитории) на соответствие HTTP API из syncbox-openapi.yaml для граничных и мусорных значений key на ЧТЕНИЕ и УДАЛЕНИЕ — GET /blobs/{key} и DELETE /blobs/{key}.

Симптом: на некоторых key, которые после percent-decode содержат управляющие символы, длинные последовательности комбинирующих диакритиков, символы дополнительных плоскостей Unicode или высокие байты Latin-1, GET/DELETE возвращают HTTP 500 (неперехваченная ошибка файловой операции — stat/read/unlink падает на непредставимом имени файла), а не код из списка ответов операции.

По схеме (syncbox-openapi.yaml) для GET /blobs/{key} допустимы 200, 404 и 400; для DELETE — 204, 404 и 400. Любой из этих кодов на таком key приемлем (в частности 404 «не найден» — валидный ответ, ключ просто не существует; 400 «недопустимый key» — тоже). Недопустим только 5xx.

Нужно:

- Обернуть операции чтения и удаления блоба (stat/exists-проверка, чтение содержимого, отправка ответа, unlink) так, чтобы сбой файловой системы на любом key давал 404 либо 400 — по твоему выбору, что естественнее для реализации, — а не неперехваченный 500. Обрабатывай класс проблемы, не конкретные байтовые последовательности из примеров.
- Обычные ключи (плоские и вложенные) должны по-прежнему давать 200/204 на существующие и 404 на отсутствующие. Уже реализованное отклонение traversal/`..`/абсолютного пути/null-байта — по-прежнему 400. PUT не трогай, его read-side это не касается.
- Добавь автоматические тесты на эти случаи, включая позитивный: легитимный key с необычной, но валидной подстрокой не должен ломаться.
- Файлы спецификации (SYNCBOX-SPEC.md, syncbox-openapi.yaml) не меняй — это внешний контракт, он уже допускает нужные коды.

После фикса перепроверь сам: подними сервер через run-server и прогони run-tests.
