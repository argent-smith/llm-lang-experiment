# Syncbox (Ruby)

Реализация [SYNCBOX-SPEC.md](SYNCBOX-SPEC.md) на Ruby 4.0.7. Весь код
исполняется в Docker; сборка, volume'ы и порты описаны в
[compose.yaml](compose.yaml), обёртки только выставляют переменные и
вызывают `docker compose`.

## Запуск

    ./run-server --data-dir <path> [--port <n>]   # по умолчанию порт 8080
    ./run-client push <dir> --server <url>        # например --server http://127.0.0.1:8080
    ./run-client pull <dir> --server <url>
    ./run-client sync <dir> --server <url>        # в обе стороны, конфликты — по правилу спецификации
    ./run-client status <dir> --server <url>      # dry-run: что загрузили бы push и скачали бы pull
    ./run-tests                                   # все тесты, код возврата != 0 при падении

Сервер: вместо флагов можно задать `SYNCBOX_DATA_DIR` / `SYNCBOX_PORT` (флаги
приоритетнее). Каталог данных создаётся при необходимости и
монтируется в контейнер, порт публикуется на хосте под тем же номером.
Сервер работает на переднем плане; SIGTERM/SIGINT (Ctrl-C) корректно
останавливает и удаляет контейнер. Если обёртку убить через SIGKILL,
убрать остатки придётся вручную (`docker compose ls`, затем
`docker compose -p <project> down`).

Клиент: `run-client <push|pull|status|sync> <dir> --server <url>`
(вместо `--server` можно задать `SYNCBOX_SERVER`, флаг приоритетнее).
`<dir>` должен существовать; он монтируется в контейнер в `/sync` — на
запись только для `pull` и `sync` (файлы создаются от имени пользователя
хоста), для `push` и `status` только на чтение. Контейнер клиента работает в сети хоста, поэтому
`--server http://127.0.0.1:<port>` указывает туда же, куда и на хосте.
Вывод (stdout/stderr) и код возврата клиента передаются как есть:
`0` — успех, `1` — ошибка (сервер недоступен, ошибка чтения/записи файла,
отказ сервера), `2` — неверные аргументы. SIGTERM/SIGINT пересылаются
клиенту в контейнер.

## Устройство

- `bin/syncbox-server` — точка входа сервера внутри контейнера.
- `lib/syncbox/server/` — конфигурация (`config.rb`), Rack-приложение
  (`app.rb`), хранилище блобов (`storage.rb`), запуск Puma (`cli.rb`).
  Блоб с ключом `docs/readme.txt` лежит в `<data-dir>/blobs/docs/readme.txt`.
- Защита от directory traversal (`Storage`) — два рубежа, любой провал
  даёт `400`. Сначала проверяется сам ключ: UTF-8 без NUL, относительный,
  без пустых сегментов, `.` и `..` (`..` также и между `\`). Затем проверяется путь:
  после нормализации он должен лежать строго внутри `<data-dir>/blobs`,
  а его родительский каталог после разрешения симлинков (`realpath`) —
  внутри разрешённого корня хранилища. Сам блоб по симлинку никогда не открывается.
- Атомарность записи (`Storage#put`): каждый `PUT` пишет тело в свой
  временный файл `<data-dir>/tmp/<случайное имя>` (+ `fsync`) и затем
  `rename` в `<data-dir>/blobs/<key>`. Читатель видит либо старый, либо
  новый блоб целиком (GET отдаёт уже открытый дескриптор), из параллельных
  `PUT` по одному ключу побеждает последний `rename`. `tmp/` лежит вне
  `blobs/`, поэтому временные файлы не попадают в `GET /blobs` и не
  адресуются никаким ключом; удаляются в `ensure` при любом исходе, а
  оставшиеся после убитого сервера — при старте. При старте же
  проверяется, что `blobs/` и `tmp/` на одной файловой системе (иначе
  `rename` не атомарен) — если нет, сервер не запускается.
- `bin/syncbox` — точка входа клиента внутри контейнера;
  `lib/syncbox/client/` — разбор аргументов (`config.rb`), обход
  локального каталога (`local_tree.rb`), HTTP-клиент на `Net::HTTP`
  (`remote.rb`), команды push (`push.rb`), pull (`pull.rb`), status
  (`status.rb`) и sync (`sync.rb`, состояние — `sync_state.rb`), коды
  возврата (`cli.rb`).
- `push`: обходит `<dir>` рекурсивно; ключ — относительный POSIX-путь
  файла (`docs/readme.txt`), в URL каждый байт кроме `[A-Za-z0-9-._~/]`
  кодируется как `%XX`. Список блобов берётся одним `GET /blobs`; файл
  загружается (`PUT`, chunked-тело), если на сервере его нет или SHA-256
  отличается (при разном размере файл не хешируется — и так ясно, что
  отличается). Совпадающие по SHA-256 файлы не загружаются; блобы, которых
  нет локально, не трогаются. На stdout — `uploaded <key>` на каждый
  загруженный файл и итог `push: N uploaded, M up to date`.
- `pull` — зеркально: блоб из `GET /blobs` скачивается (`GET /blobs/{key}`)
  в `<dir>/<key>`, если локального файла нет или SHA-256 отличается;
  недостающие подкаталоги создаются. Совпадающие файлы не скачиваются и не
  трогаются, локальные файлы без блоба на сервере не удаляются. Ключи от
  сервера не доверенные: ключ, который не является путём внутри `<dir>`
  (`..`, абсолютный, пустые сегменты, `.`, NUL), — ошибка ещё до
  скачивания чего-либо; симлинки по пути к файлу не разыменовываются
  (блоб пропускается с предупреждением, как и симлинк на месте файла).
  Каталог на месте файла или файл на месте каталога — ошибка. Запись
  атомарная: тело пишется во временный `.syncbox-pull-<случайное>` рядом с
  целевым файлом (+ `fsync`), затем `rename`; при ошибке старый файл
  остаётся как был, временный удаляется (остаться он может только после
  SIGKILL). Заменённый файл сохраняет права доступа. Обрезанное тело
  ответа (меньше `Content-Length`) — ошибка. Блоб, удалённый с сервера
  между списком и скачиванием, пропускается с предупреждением. На stdout —
  `downloaded <key>` и итог `pull: N downloaded, M up to date`.
- `status` — dry-run `push` и `pull` разом: один `GET /blobs`, сравнение
  с `<dir>` по ключу и SHA-256 по тем же правилам, что у `push` и `pull`
  (те же пропуски симлинков и спецфайлов, та же проверка ключей сервера), и
  отчёт на stdout, например:

      upload (not on server): dir/new.txt
      upload (content differs): notes.txt
      download (not local): photos/cat.jpg
      download (content differs): notes.txt
      status: 2 to upload, 2 to download, 3 up to date

  `upload` — что загрузил бы `push`, `download` — что скачал бы `pull`;
  файл с разным содержимым попадает в оба списка (кто из сторон победит,
  решает `sync`). Без расхождений — одна строка
  `status: nothing to upload or download, N up to date`. Код возврата `0`
  при любом количестве расхождений. Ничего не меняет: других запросов к
  серверу нет, локальные файлы только читаются (и каталог смонтирован в
  контейнер только на чтение).
- `sync` — `push` и `pull` за один проход: один `GET /blobs`, затем по
  каждому ключу (в порядке ключей) одно из:
  - файл только локально → `PUT`; блоб только на сервере → скачивание
    (как у `pull`, с созданием подкаталогов);
  - SHA-256 совпадают → ничего;
  - различаются, и одна сторона совпадает с последней общей версией →
    изменилась только другая, её версия и переносится (время изменения
    тогда не важно);
  - различаются, и ни одна сторона не совпадает с последней общей версией
    (изменены обе, или общей версии нет — первый `sync`, файл появился на
    обеих сторонах независимо) → конфликт по правилу спецификации:
    побеждает более свежий `modified_at` сервера / mtime локального файла,
    при равенстве — локальная версия. mtime сравнивается с точностью
    `modified_at` (наш сервер отдаёт микросекунды): лишние знаки mtime
    отбрасываются.

  Ничего не удаляется: файл, удалённый на одной стороне, на следующем
  `sync` снова приходит с другой. На stdout — `uploaded <key>` /
  `downloaded <key>` (у разрешённого конфликта с пометкой, например
  `uploaded notes.txt (conflict: local copy is newer)`) и итог
  `sync: N uploaded, M downloaded, K up to date`. Всё сравнение (и
  хеширование) делается до первого переноса, так что локальное
  препятствие (каталог на месте файла и т. п.) или недопустимый ключ
  сервера роняют `sync` до изменений.
- Последняя общая версия хранится в `<dir>/.syncbox/state.json`: для
  каждого URL сервера — SHA-256 каждого файла, который после `sync`
  совпадал на обеих сторонах (для загруженного — SHA-256 из ответа `PUT`,
  для скачанного — от записанных байт). Пишется атомарно (временный файл в
  `.syncbox/` + `rename`) в конце `sync`, только если что-то изменилось
  (если `sync` оборвался на ошибке, состояние не пишется — уже перенесённые
  файлы на следующем запуске просто совпадут на обеих сторонах).
  Пропущенные файлы (симлинк и т. п.) сохраняют прежнюю запись. Битый файл
  состояния — ошибка (`remove it to start afresh`), а не молчаливый сброс:
  без общей версии расхождения решались бы по времени. Каталог `.syncbox`
  в корне `<dir>` — служебный для всех команд: `push`/`status`/`sync` его
  не видят, блобы с ключами `.syncbox` и `.syncbox/...` `pull`/`status`/`sync`
  пропускают с предупреждением.
- Симлинки и специальные файлы (FIFO, сокеты, устройства) не
  синхронизируются: пропускаются с предупреждением в stderr. Имя файла не
  в UTF-8 ключом быть не может — это ошибка. Пока при первой же ошибке
  (сеть, чтение/запись файла, отказ сервера) `push`/`pull`/`status`/`sync` останавливается
  с сообщением в stderr и кодом 1; продолжение после частичных сбоев и итоговый отчёт —
  тикет 11.
- `scripts/compose.sh` — общая логика обёрток: отдельный compose-проект
  на каждый запуск, проброс сигналов (клиенту — прямо в контейнер),
  `down` при выходе.
- `test/` — minitest: юнит-тесты сервера (`test/*_test.rb`) и клиента
  (`test/client/`), интеграционные тесты процессов сервера и клиента по
  реальному HTTP.

Gemfile.lock пересобирается внутри контейнера, например
`docker compose run --rm -v "$PWD":/app test bundle lock`.
