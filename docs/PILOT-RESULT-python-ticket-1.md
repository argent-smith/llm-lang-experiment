## Итог

Тикет 1 (каркас сервера Syncbox) сошёлся на Python после устранения
методологической контаминации, обнаруженной в первом прогоне. Прогон 2
ниже (2026-08-19) на момент записи считался принятой точкой данных, но
2026-08-20 задним числом аннулирован — использовал устаревшую,
не до конца зачищенную копию спецификации (см.
[дополнение к инциденту](incidents/2026-08-19-python-ticket1-contamination/README.md#устаревшая-копия-спецификации-2026-08-20)).
Прогон 3 (2026-08-20, `session_id 15b12587-...`) был действующей точкой
данных под тогдашней финальной версией харнеса
(`--dangerously-skip-permissions`, синхронизация спецификации перед
каждым вызовом) — аннулирован задним числом 2026-08-24: после находки,
что внутренняя файловая песочница Claude Code не покрывает инструменты
Read/Write (см.
[инцидент](incidents/2026-08-21-write-tool-sandbox-escape/README.md)),
весь пилот Python+Go переигран под Docker-обвязанным харнессом
(`scripts/pilot-harness.Dockerfile`). Прогон 4 (2026-08-24, `session_id
c3ba09eb-...`) был действующей точкой данных на новом харнессе — тоже
аннулирован задним числом 2026-08-25: харнес не фиксировал `--effort`
явно, и дефолт CLI оказался `high`, не `xhigh`, как везде остальные
(найдено `grep`-проверкой по `transcript.jsonl`, не документацией).
**Действующая точка данных — прогон 5 ниже** (2026-08-25, `session_id
81c45f42-...`, `effort=xhigh` подтверждён).

## Аудит соответствия спецификации (тикеты 1–3)

Изначально проведён на прогонах старого харнеса (2026-08-20), повторно
подтверждён вручную на канонических прогонах 2026-08-25 (Docker-харнесс,
`effort=xhigh`, `session_id` выше) — те же коды ответов и форма JSON,
включая независимую сверку `sha256`/`size`/`modified_at` через прямой
`curl` к `run-server`. Короткая проверка по чек-листу из плана
верификации — против `docs/SYNCBOX-SPEC.md`/`docs/syncbox-openapi.yaml`:

- HTTP-поверхность (`/healthz`, `PUT`/`GET /blobs/{key}`, `GET /blobs`)
  реализована буквально по спецификации — коды ответов, форма JSON
  (`{"key", "sha256", "size"}` для PUT, `{"key", "size", "sha256",
  "modified_at"}` для списка) совпадают дословно, лишних полей и
  эндпоинтов нет.
- CLI/обёртки (`run-server`) не менялись с тикета 1 — агент явно не
  трогал их в тикетах 2–3, если не требовалось.
- Docker-хозяйство — только `docker compose`, без голых `docker
  run`/`build`, не менялось с тикета 1.
- Границы тикетов соблюдены буквально в обе стороны: агент не
  забегал вперёд (защита от traversal и атомарность записи, обе явно
  описанные в спецификации как обязательные для `PUT`, сознательно не
  реализованы в тикете 2) и не пропускал часть объявленного тикета.

Итог: на Python отклонений от спецификации не найдено — хорошая база
для сравнения, когда появится второй язык.

## Code quality

На прогонах старого харнеса (2026-08-20) тулинг появился уже после
того, как все три тикета прошли — тот замер был разовым ретроактивным
сканом финального состояния кода (после тикета 3): 2 находки `E501`
(строка длиннее 88 символов) в `server/main.py`. На канонических
прогонах Docker-харнеса (2026-08-25, `effort=xhigh`) code quality —
часть автоматической архивации на каждый тикет
(`scripts/run-pilot-ticket.sh`), не ретроактивный снимок: тикет 1 —
5 находок, `PLR2004` («magic value» на литералах HTTP-статусов/портов
в тестах) ×4, `I001` (неотсортированный блок импортов) ×1 — конфиг
`scripts/code-quality-configs/python/ruff.toml`, версия 0.16.4. Ни в
одном из трёх замеров (старый харнесс, раунд effort=high, раунд
effort=xhigh) — не критерий «сошлось/сдалось» (CLAUDE.md, раздел
«Метод»), только данные для последующего анализа. Полная динамика по
всем трём тикетам — в
[`docs/PILOT-COMPARISON-python-go.md`](PILOT-COMPARISON-python-go.md).

Code security (bandit) гоняли на старом прогоне — 1 находка
(`B104 hardcoded_bind_all_interfaces`, severity=MEDIUM). Проверку
убрали из метода: см.
[`docs/PILOT-COMPARISON-python-go.md`](PILOT-COMPARISON-python-go.md#code-quality--code-security-исключено),
там разбор, почему сравнение находок между языками оказалось
неинформативным.

## Что дальше

Актуализировано после переигровки пилота Python+Go на Docker-харнессе
под явным `effort=xhigh` (2026-08-25, см.
[`docs/PILOT-RESULT-go.md`](PILOT-RESULT-go.md) и
[`docs/PILOT-COMPARISON-python-go.md`](PILOT-COMPARISON-python-go.md))
— из трёх открытых рисков пилотной фазы (CLAUDE.md, «Сначала пилот»):

- Утечка контекста метарепозитория — закрыта в два раунда. Раунд 1
  верифицирован на двух языках под старым харнессом (Python 3 тикета,
  Go 3 тикета, 0 совпадений по расширенному набору терминов); попутно
  вскрылись два дополнительных канала (устаревшая копия спецификации,
  `dangerouslyDisableSandbox`), оба закрыты процессными фиксами. Раунд
  2 (2026-08-21): аудит показал, что вся файловая песочница раунда 1
  была структурно нерабочей для Read/Write — фикс (весь `claude -p`
  внутри Docker-контейнера с единственной примонтированной директорией
  пилота) подтверждён на реальных тикетах (весь пилот Python+Go
  переигран под ним, все 6 тикетов сошлись, транскрипты архивированы).
  См. [инцидент раунда 2](incidents/2026-08-21-write-tool-sandbox-escape/README.md).
- Соответствие спецификации между языками — Python и Go пройдены без
  отклонений на всех харнессах (см. аудит в обоих pilot-result-
  документах): HTTP-контракт и границы тикетов соблюдены дословно.
  Один показательный, не проблемный результат гипотезы, который
  изменился между раундами: на старом харнессе Go писал юнит-тесты на
  всех трёх тикетах, Python — ни разу; на Docker-харнессе (начиная с
  2026-08-24) оба языка написали тесты на всех тикетах —
  `SYNCBOX-SPEC.md` с 2026-08-20 явно требует штатные тесты, чего не
  было в силе на прогонах старого харнеса для Python.
- Устойчивость цикла `-p` → `--resume` к рейт-лимитам — первый живой
  сигнал получен 2026-08-24 (Go, тикет 2, переигровка на Docker-
  харнессе): `429 session limit`, фиксированное окно использования с
  точным временем сброса в самом ответе API, не хаотичный бэкофф-
  рейт-лимит. Прогон просто повторён после сброса, само по себе
  воспроизводимо. Попутная находка того же прогона — упавший вызов
  обрывал скрипт архивации до сохранения результата (`set -e` без
  перехвата кода возврата), потерянная попытка восстановлена вручную
  из зафиксированного вывода, фикс (`CLAUDE_EXIT`) внесён в
  `scripts/run-pilot-ticket.sh` сразу после находки — см. `NOTE.md` в
  `docs/pilot-runs/go/ticket-2/47ced9a7-.../`. Полноценного стресс-теста
  цикла `--resume` это по-прежнему не даёт (все канонические тикеты
  сошлись за одну итерацию каждый) — остаётся открытым для следующих
  языков. Ранее вскрывались и два смежных, не предполагавшихся риска
  того же семейства — headless-надёжность самого вызова харнеса:
  `--permission-mode dontAsk` один раз молча отклонил все правки (см.
  [инцидент](incidents/2026-08-20-dontask-permission-denial/README.md));
  и Docker-сборка внутри песочницы дважды подряд деградировала до
  проверки без Docker E2E (см.
  [инцидент](incidents/2026-08-20-docker-build-sandbox-gaps/README.md)).
  Общий урок пилотной фазы: «прогон вышел кодом 0» не равно «прогон
  сделал то, что нужно», а «эффективный параметр запуска совпадает с
  задокументированным» тоже нельзя предполагать — только явная
  фиксация (модель, effort) и проверка по транскрипту, не по тексту
  скрипта, ловит дрейф вроде `effort=high` вместо `xhigh`.
