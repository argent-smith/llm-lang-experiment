## Аудит соответствия спецификации (тикеты 1–3)

Короткая проверка по чек-листу из плана верификации — против
`docs/SYNCBOX-SPEC.md`/`docs/syncbox-openapi.yaml`:

- HTTP-поверхность (`/healthz`, `PUT`/`GET /blobs/{key}`, `GET /blobs`)
  реализована буквально по спецификации — коды ответов, форма JSON
  (`{"key", "sha256", "size"}` для PUT, `{"key", "size", "sha256",
  "modified_at"}` для списка) совпадают дословно, лишних полей и
  эндпоинтов нет.
- CLI/обёртки (`run-server`) не менялись с тикета 1 — агент явно не
  трогал их в тикетах 2–3, если не требовалось.
- Docker-хозяйство — только `docker compose`, без голых `docker
  run`/`build`, не менялось с тикета 1.
- Границы тикетов соблюдены буквально в обе стороны: агент не
  забегал вперёд (защита от traversal и атомарность записи, обе явно
  описанные в спецификации как обязательные для `PUT`, сознательно не
  реализованы в тикете 2 — оба самоотчёта прямо это фиксируют: «Directory-traversal
  protection, atomic writes... are intentionally left out, per the
  ticket's scope») и не пропускал часть объявленного тикета.

Итог: на Python отклонений от спецификации не найдено — хорошая база
для сравнения, когда появится второй язык.

## Code quality / code security (ретроактивно)

Тулинг (`scripts/run-code-quality.sh`) появился 2026-08-20, после того
как все три тикета Python уже прошли — это разовый ретроактивный скан
финального состояния кода (после тикета 3), не результат по каждому
тикету отдельно (директория пилота не git-репозиторий, промежуточных
срезов нет). Не входит в критерий «сошлось/сдалось» (CLAUDE.md,
раздел «Метод») — только данные для последующего анализа.

**Ruff (quality):** 0 находок.

**Bandit (security):** 1 находка.

- `B104 hardcoded_bind_all_interfaces`: Possible binding to all
  interfaces (severity=MEDIUM, confidence=MEDIUM) — `server/main.py:43`.
  По существу — сервер слушает на всех интерфейсах внутри контейнера,
  что обычно и требуется, чтобы порт был доступен снаружи контейнера
  (иначе `--data-dir`/`--port` через Docker вообще не имели бы смысла);
  Bandit не знает о контейнеризации и всегда помечает bind-all как
  находку среднего риска — не обязательно дефект в контексте этого
  проекта, но зафиксировано как есть, без ручной фильтрации находок.

## Что дальше

Актуализировано после пилота на Go (второй язык, см.
[`docs/PILOT-RESULT-go.md`](PILOT-RESULT-go.md)) — из трёх открытых
рисков пилотной фазы (CLAUDE.md, «Сначала пилот»):

- Утечка контекста метарепозитория — верифицирована на двух языках
  (Python 3 тикета, Go 3 тикета, все прогоны под финальным харнесом,
  0 совпадений по расширенному набору терминов, включая имена всех
  шести языков). Ходом пилота вскрылись два дополнительных, изначально
  не предполагавшихся канала: устаревшая копия спецификации (закрыта
  синхронизацией перед каждым вызовом) и возможность агента самому
  снять файловую песочницу через `dangerouslyDisableSandbox` (закрыта
  `sandbox.allowUnsandboxedCommands: false`, найдено на Go — на
  Python этот канал не проявлялся, потому что песочница почти не
  создавала поводов её обходить). Оба закрыты процессными фиксами
  в `scripts/run-pilot-ticket.sh`, не разовыми правками.
- Соответствие спецификации между языками — Python и Go пройдены без
  отклонений (см. аудит в обоих pilot-result-документах): HTTP-контракт
  и границы тикетов соблюдены дословно на обоих языках. Один
  показательный, не проблемный результат гипотезы: Go писал юнит-тесты
  на всех трёх тикетах, Python — ни разу.
- Устойчивость цикла `-p` → `--resume` к рейт-лимитам — по-прежнему не
  проверялась впрямую (все 6 тикетов на двух языках сошлись за одну
  итерацию каждый — смок/контракт остаются н/п до тикетов 4–7). Зато
  вскрылись два смежных, не предполагавшихся риска того же
  семейства — headless-надёжность самого вызова харнеса:
  `--permission-mode dontAsk` один раз из четырёх прогонов молча
  отклонил все правки (CLI вышел кодом 0, ничего не сделав) — см.
  [инцидент](incidents/2026-08-20-dontask-permission-denial/README.md);
  и Docker-сборка внутри песочницы дважды подряд деградировала до
  проверки без Docker E2E из-за сетевых/файловых ограничений,
  замаскированных до этого закрытой лазейкой
  `dangerouslyDisableSandbox` — см.
  [инцидент](incidents/2026-08-20-docker-build-sandbox-gaps/README.md).
  Оба зафиксированы фиксами, но само явление — предупреждение на
  будущее: «прогон вышел кодом 0» не равно «прогон сделал то, что
  нужно», проверять нужно и то, и другое на каждом новом языке, а не
  только один раз.
