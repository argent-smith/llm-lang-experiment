# Результат пилота: Python, тикет 1

## Итог

Тикет 1 (каркас сервера Syncbox) сошёлся на Python после устранения
методологической контаминации, обнаруженной в первом прогоне. Прогон 2
ниже (2026-08-19) на момент записи считался принятой точкой данных, но
2026-08-20 задним числом аннулирован — использовал устаревшую,
не до конца зачищенную копию спецификации (см.
[дополнение к инциденту](incidents/2026-08-19-python-ticket1-contamination/README.md#устаревшая-копия-спецификации-2026-08-20)).
Действующая точка данных для тикета 1 — прогон 3 ниже
(2026-08-20, `session_id 15b12587-...`), под финальной версией харнеса
(`--dangerously-skip-permissions`, синхронизация спецификации перед
каждым вызовом). Харнесс (`scripts/run-pilot-ticket.sh`) в текущем виде
готов к переиспользованию на следующих тикетах и языках.

## Аудит соответствия спецификации (тикеты 1–3)

Короткая проверка по чек-листу из плана верификации — против
`docs/SYNCBOX-SPEC.md`/`docs/syncbox-openapi.yaml`:

- HTTP-поверхность (`/healthz`, `PUT`/`GET /blobs/{key}`, `GET /blobs`)
  реализована буквально по спецификации — коды ответов, форма JSON
  (`{"key", "sha256", "size"}` для PUT, `{"key", "size", "sha256",
  "modified_at"}` для списка) совпадают дословно, лишних полей и
  эндпоинтов нет.
- CLI/обёртки (`run-server`) не менялись с тикета 1 — агент явно не
  трогал их в тикетах 2–3, если не требовалось.
- Docker-хозяйство — только `docker compose`, без голых `docker
  run`/`build`, не менялось с тикета 1.
- Границы тикетов соблюдены буквально в обе стороны: агент не
  забегал вперёд (защита от traversal и атомарность записи, обе явно
  описанные в спецификации как обязательные для `PUT`, сознательно не
  реализованы в тикете 2 — оба самоотчёта прямо это фиксируют: «Directory-traversal
  protection, atomic writes... are intentionally left out, per the
  ticket's scope») и не пропускал часть объявленного тикета.

Итог: на Python отклонений от спецификации не найдено — хорошая база
для сравнения, когда появится второй язык.

## Что дальше

Из трёх открытых рисков пилотной фазы (CLAUDE.md, «Сначала пилот»):

- Утечка контекста метарепозитория — верифицирована трижды на Python
  (тикеты 1–3, прогоны под финальным харнесом), но по-прежнему только
  на одном языке. Ходом пилота вскрылся дополнительный, изначально не
  предполагавшийся канал (устаревшая копия спецификации, не
  синхронизировавшаяся с правками в мета-репозитории) — закрыт
  процессным фиксом в `scripts/run-pilot-ticket.sh`, а не разовой
  правкой файла, что делает риск устойчивее к будущим правкам
  спецификации.
- Соответствие спецификации между языками — пилот Python (3 тикета)
  завершён без отклонений (см. аудит выше), но сравнивать пока не с
  чем: нужен минимум ещё один язык, чтобы судить о риске по существу.
- Устойчивость цикла `-p` → `--resume` к рейт-лимитам — пока не
  проверялась: все прогоны тикетов 1–3 сошлись за одну итерацию,
  самого цикла ревью с `--resume` ещё не было (смок/контракт остаются
  н/п до тикетов 4–7, а именно они — реалистичный источник внешней
  обратной связи, запускающей `--resume`). Зато вскрылся смежный, не
  предполагавшийся риск того же семейства — headless-надёжность
  самого вызова харнеса: `--permission-mode dontAsk` один раз из
  четырёх прогонов молча отклонил все правки, не дав об этом знать
  иначе как через код результата и текст самоотчёта модели (CLI при
  этом вышел кодом 0). См.
  [инцидент](incidents/2026-08-20-dontask-permission-denial/README.md).
  Зафиксирован фикс (`--dangerously-skip-permissions`), но само явление
  — предупреждение на будущее: «прогон вышел кодом 0» не равно «прогон
  что-то сделал», проверять нужно и то, и другое.
