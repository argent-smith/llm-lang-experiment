# Инцидент: файловая песочница Claude Code не покрывает Read и Write

Дата обнаружения: 2026-08-21. Повод — не находка на живом прогоне, а
предупреждающий вопрос до него: должна ли изоляция пилотных стендов
дополнительно исключать «подглядывание» агента в уже сошедшиеся
реализации на других языках (`docs/pilot-runs/`, соседние
`syncbox-<язык>/`). Проверка этого вопроса вскрыла, что вся файловая
песочница, зафиксированная фиксом
[2026-08-19](../2026-08-19-python-ticket1-contamination/README.md) и
уточнённая фиксом
[2026-08-20](../2026-08-20-sandbox-escape-hatch/README.md), была
структурно иллюзорной для двух из трёх файловых инструментов агента.

## Что обнаружено

`sandbox.filesystem.denyRead`/`allowRead`, передаваемые через
`--settings`, управляют только тем, как Bash-подпроцессы Claude Code
видят файловую систему (через `sandbox-exec` на macOS/аналог на Linux).
Инструменты **Read** и **Write** — не Bash-подпроцессы, у них
собственный путь исполнения:

- **Read** де-факто игнорирует `denyRead` целиком. Единственная
  проверка перед чтением — система разрешений (`permissions.allow/deny`
  с правилами вида `Read(path)`), а её `--dangerously-skip-permissions`
  отключает полностью. Наш собственный харнес именно этот флаг и
  передавал (см. [инцидент про `dontAsk`](../2026-08-20-dontask-permission-denial/README.md))
  — значит Read был не ограничен вообще ничем с самого начала пилота.
- **Write** не поддерживает ограничение по пути ни в каком режиме
  разрешений — ни `allow`, ни `deny`, ни `--settings`. Подтверждено
  трижды: диагностическим прогоном с явным запретом на путь вне
  директории пилота (запись прошла), повторной проверкой с
  `permissions.deny: ["Write(//Users/**)"]` в `--settings` (запись всё
  равно прошла), и официальной документацией
  (`code.claude.com/docs/en/permissions.md`), где path-scoping явно
  описан только для файловых инструментов чтения/редактирования, не
  для Write.

Иными словами: с самого первого пилотного прогона (тикет 1, Python,
2026-08-19) агент технически мог прочитать что угодно на хосте,
доступное текущему пользователю ОС, и записать что угодно куда угодно
— файловая песочница `--settings` создавала иллюзию границы только
для Bash-инструментов (`cat`, `cp`, перенаправление вывода), но не для
основных инструментов редактирования кода.

## Аудит уже состоявшихся прогонов

Все 6 реальных пилотных прогонов на момент находки (Python тикеты 1–2,
Go тикеты 1–3, плюс переигровка тикета 1 Python) проверены построчно —
не поиском по ключевым словам, а разбором каждого вызова инструментов
`Write`/`Edit`/`Read` в JSONL-транскрипте сессии с сверкой `file_path`
против единственного разрешённого префикса (директория пилота). Ни
один вызов не вышел за пределы своей директории ни в одном из 6
прогонов. Находка — про открытую возможность, не про случившуюся
эксплуатацию: методологическая гарантия была бумажной, но по факту не
нарушалась случайно.

## Рассмотренные варианты фикса

Сравнивались два способа дать реальную, не только внутреннюю для
Claude Code, границу:

1. **macOS `sandbox-exec`** — тот же примитив, которым Claude Code сам
   пользуется для Bash-подпроцессов, применённый к самому процессу
   `claude -p`. Отклонён: platform-specific (только macOS, а CI и
   потенциальные коллеги — Linux), `sandbox-exec` официально
   deprecated с угрозой удаления, и типобезопасно накрыть именно
   Read/Write инструменты Claude Code (не файловые сисколы вообще)
   профилем `sandbox-exec` не проще, чем сделать то же средствами ОС
   контейнера.
2. **Docker-контейнер** — обернуть весь вызов `claude -p` в контейнер,
   где смонтирована только директория пилота
   (`-v $PILOT_DIR:/workspace`). Выбран: кросс-платформенно (macOS/Linux
   одинаково, воспроизводимо для коллег), изоляция обеспечивается ядром
   (Linux-namespaces), не самим Claude Code — агент не может отключить
   её изнутри никаким параметром инструмента, в отличие от
   `dangerouslyDisableSandbox` из предыдущего инцидента. Если путь не
   примонтирован, его физически нет в файловой системе процесса — Read
   получает «файл не существует», Write получает то же самое (или пишет
   в **собственный**, не примонтированный `/tmp` контейнера, который
   уничтожается вместе с контейнером и никогда не попадает на диск
   хоста).

## Реализация

- `scripts/pilot-harness.Dockerfile` — `node:22-slim` + `docker`
  CLI/compose-плагин, скопированные из `docker:27-cli` (не
  `apt-get install docker.io` — та версия не даёт compose), Claude Code
  установлен с закреплённой версией (не `@latest` — тот же принцип, что
  и точный ID модели). Пользователь — непривилегированный `node`
  (`--dangerously-skip-permissions` отказывается работать под
  root/sudo).
- Docker-out-of-Docker: `/var/run/docker.sock` хоста пробрасывается
  внутрь контейнера харнеса, чтобы агент мог собирать и тестировать
  контейнер кода тикета как соседний, не вложенный. На Docker Desktop
  (macOS) примонтированный сокет виден изнутри контейнера как
  `root:root`, `rw-rw----` — не так, как показывает `ls` на хосте (там
  `paul:staff`): VM-прослойка Docker Desktop (gRPC-FUSE/VirtioFS)
  переинтерпретирует владение файлом на границе. Значение имеет только
  то, что видно **изнутри** контейнера — фикс: `usermod -aG root node`
  (группа `root`, gid 0), не попытка угадать GID хостовой группы
  `staff`.
- `scripts/run-pilot-ticket.sh` переписан: вместо прямого вызова
  `claude -p` на хосте — `docker run --rm -i` с `-v
  "$PILOT_DIR:/workspace:rw"` и `-v "$DOCKER_SOCK:/var/run/docker.sock"`
  (путь к сокету — через `docker context inspect`, не хардкод
  `/var/run/docker.sock`, чтобы работать одинаково на Docker
  Desktop/macOS и Docker Engine/Linux). Внутренние
  `sandbox.filesystem.denyRead`/`allowRead` через `--settings` убраны —
  внутри контейнера, где ничего, кроме `/workspace`, не смонтировано,
  ограничивать по пути больше нечего; `--safe-mode` оставлен как
  дешёвая защита на случай, если образ харнеса когда-нибудь обзаведётся
  собственным CLAUDE.md.
- OAuth-токен передаётся в контейнер через `--env-file
  scripts/pilot-harness.env` (гитигнорится, реальный секрет никогда не
  коммитится и не печатается) — см. `scripts/pilot-harness.env.example`.

### Побочные находки при реализации

Две проблемы обнаружены и исправлены по пути, не связаны с
безопасностью напрямую, но без них харнес не работал:

- Образ харнеса был изначально назван `syncbox-pilot-harness` — под
  этим именем он совпадал с фильтром `reference=syncbox*` в собственной
  же чистке Docker-демона (`scripts/run-pilot-ticket.sh`, предназначена
  для образов кода тикетов) и удалялся сразу после сборки, до
  использования. Переименован в `pilot-harness` (без префикса
  `syncbox`).
- Docker Desktop с containerd image store (включён по умолчанию) не
  может протегировать образ, экспортированный `docker build` с
  attestation-манифестом по умолчанию: сборка рапортует «naming to ...
  done», но `docker images`/`docker run` образ не находят.
  Воспроизведено эмпирически; фикс — `docker build --provenance=false
  --sbom=false`.

## Верификация

Диагностический прогон против временной директории (не пилотный
проект, не идёт в архив/лог эксперимента):

1. Write внутри `/workspace` — файл создан, виден на хосте.
2. Read `/Users/<user>/work/syncbox-python/server/app.py` (реальный файл
   на хосте, не примонтированный внутрь) — не удалось, путь не
   существует внутри контейнера.
3. Write `/tmp/probe-outside.txt` — прошло **внутри контейнера**, но на
   диске хоста файла нет: `/tmp` контейнера не примонтирован, это
   собственная, эфемерная файловая система контейнера, уничтожается
   вместе с ним (`--rm`).
4. `docker ps` изнутри контейнера — успешно, виден демон хоста
   (Docker-out-of-Docker для сборки кода тикета работает).

Отдельно — полный прогон `scripts/run-pilot-ticket.sh` целиком (сборка
образа, чистка Docker-демона, вызов `claude -p` в контейнере, запись
файла, архивация в `docs/pilot-runs/`) на тестовом тикете подтвердил
работоспособность всей цепочки end-to-end; тестовые артефакты не
сохранены — не часть эксперимента.

## Что не переигрывается

Уже состоявшиеся 6 прогонов (Python тикеты 1–2, Go тикеты 1–3) не
переигрываются: построчный аудит подтвердил, что реальной
эксплуатации не было, а фикс меняет только границу для последующих
прогонов, не переписывает прошлое. Все дальнейшие тикеты пилота (и
последующий полный прогон, если пилот сойдётся) идут через
Docker-обёрнутый харнес.
