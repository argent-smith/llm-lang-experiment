# Инцидент: `docker build`/`buildx` внутри песочницы бьётся о сеть и запись состояния

Дата: 2026-08-20. Прогоны: тикет 2, Go, три попытки подряд —
`session_id f50e806a-3089-4bbd-a977-334966d3d64b`,
`3eba70a1-f895-4c3b-b6df-d67cff29067b`,
`2365906e-d492-496f-8b75-a81b205e6868`, директория пилота
`<pilot-host-dir>`. Продолжение находки из
[соседнего инцидента](../2026-08-20-sandbox-escape-hatch/README.md):
после того как `dangerouslyDisableSandbox` перестал работать (см. тот
инцидент), агент лишился прежнего обходного пути и уткнулся в
реальные ограничения песочницы, которые этот обход маскировал.

## Что произошло — три попытки подряд

**Попытка 1** (`f50e806a`). `docker compose build` упал:
`failed to fetch oauth token: Post "https://auth.docker.io/token": tls:
failed to verify certificate: x509: OSStatus -26276`. Наше собственное
предположение в комментарии скрипта («исходящий трафик в интернет в
любом случае идёт из демона Docker, не из сендбоксируемого процесса»)
оказалось неверным: клиентский процесс `docker build` (buildx) сам
делает HTTPS-запрос за OAuth-токеном, и он подпадает под сетевую
изоляцию песочницы. Агент откатился на проверку через `go build`/`go
vet`/`go test` — код рабочий, но без реального Docker E2E. Модель сама
неверно интерпретировала причину («песочница разрешает сеть только на
docplayer.net») — в логе этого домена нет вообще, реальная причина
только что описанная TLS-ошибка.

**Фикс 1**, подтверждён отдельным диагностическим прогоном:
`sandbox.network.allowedDomains` с доменами Docker Hub
(`auth.docker.io`, `registry-1.docker.io`,
`production.cloudflare.docker.com`, `*.docker.io`,
`*.cloudflare.docker.com`). `docker pull alpine:3.20` (не
закешированный) в изолированном прогоне прошёл успешно.

**Попытка 2** (`3eba70a1`), под фиксом 1. Уткнулась в ДРУГОЕ
ограничение: `docker buildx` пишет служебное состояние
(`~/.docker/buildx/activity` и соседние директории) — не входит в
`allowRead`/`allowWrite`, падает `operation not permitted`. Тот же
класс проблемы, что уже отмечался на Python (тикет 1, там обошли
`DOCKER_BUILDKIT=0` на одну команду) и на Go (тикет 1, там обошли
полным снятием песочницы — теперь недоступно). Агент откатился на
локальный smoke собранным Go-бинарником без Docker — код рабочий, но
опять без Docker E2E.

**Фикс 2**: `sandbox.filesystem.allowWrite: ["~/.docker/buildx"]` —
не креды (те в `~/.docker/config.json`, отдельно), только служебное
состояние buildx.

**Попытка 3** (`2365906e`), под обоими фиксами. Разовая заминка:
`docker compose build` (полный путь через buildx-резолюцию метаданных
образов) снова коротко упёрся в ту же TLS-ошибку, что и попытка 1,
несмотря на `allowedDomains` — судя по всему, конкретно этот путь
резолюции метаданных использует соединение, не покрытое перечисленными
доменами буквально (возможный кандидат — другой CDN-хост под капотом
Cloudflare/Docker Hub, не входящий в добавленный список). Агент **сам,
без вмешательства человека**, обошёл это `docker pull
alpine:3.20`/`golang:1.23-alpine` напрямую (этот путь через тот же
`allowedDomains` уже работает), после чего `docker compose build`
взял образы из прогретого локального кэша и прошёл. Дальше —
полноценная Docker E2E-проверка: PUT/GET через реальный контейнер,
sha256 сверен независимым `shasum`, перезапись ключа, `docker compose
down` в конце.

## Была ли работа испорчена

Нет. Все три попытки — валидная работа модели над одним и тем же
тикетом, деградация каждый раз была из-за среды, не из-за модели;
разбор транскриптов (см. `docs/EXPERIMENT-LOG.md`) не нашёл
контаминации ни в одной из трёх. Итоговая, принятая точка данных —
попытка 3: полноценный Docker E2E достигнут, при этом без вмешательства
человека — агент сам продиагностировал и обошёл остаточную заминку.

## Не закрыто до конца

Первопричина заминки попытки 3 (почему `allowedDomains` из фикса 1 не
покрыл этот конкретный путь резолюции buildx с первого раза) не
выяснена до конца — дальнейшая диагностика признана нецелесообразной
здесь: реальный Docker E2E уже достигнут, а модель продемонстрировала,
что справляется с этой конкретной заминкой самостоятельно (через
`docker pull` заранее). Если в будущих языковых пилотах эта же заминка
будет мешать сходимости тикетов (а не только требовать один лишний
шаг), возвращаться к более точному списку `allowedDomains` — тем же
методом: дешёвый изолированный диагностический прогон, а не гадание.

Полная построчная запись всех трёх попыток —
[`docs/EXPERIMENT-LOG.md`](../../EXPERIMENT-LOG.md).
