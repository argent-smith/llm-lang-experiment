# Инцидент: агент может сам снять файловую песочницу через `dangerouslyDisableSandbox`

Дата: 2026-08-20. Прогон: тикет 1, Go, `session_id`
`cc042dab-159b-4b14-8bd0-b6912e012bbb`, директория пилота
`<pilot-host-dir>`. Утечки не произошло — это находка о
незакрытой возможности, а не разбор случившейся контаминации.

## Что произошло

В самоотчёте агент упомянул: «Проверено вручную (со снятой
песочницей — `docker buildx` пишет в `~/.docker/buildx/activity`, вне
разрешённых путей)». Разбор транскрипта показал 18 вызовов Bash с
параметром `dangerouslyDisableSandbox: true` — стандартным параметром
инструмента Bash, отключающим `sandbox.filesystem` на конкретную
команду. Причина та же, что уже отмечалась на Python (тикет 1,
переигровка): `docker buildx` пишет служебные файлы в
`~/.docker/buildx/activity`, не входящий в `allowRead`, и падает с
«operation not permitted». На Python агент обошёл это переключением на
классический билдер (`DOCKER_BUILDKIT=0`) для одной команды; на Go —
снятием песочницы целиком для тех же по смыслу диагностических команд
(запуск `run-server`, `curl` к `/healthz`, `docker ps`, отправка
`SIGTERM`, уборка).

Построчный разбор всех 18 команд (см. процедуру ниже) — ни одна не
читает и не пытается прочитать что-либо за пределами
`<pilot-host-dir>` и собственного scratchpad-каталога сессии.
Утечки не было. Но сама возможность оказалась открыта не по недосмотру
в тексте спецификации (как в исходном инциденте про
`reference-impl`), а по устройству харнеса: под
`--dangerously-skip-permissions` использование
`dangerouslyDisableSandbox` не требует ничьего подтверждения — решение
целиком на усмотрение модели.

## Причина

`--settings`, генерируемые `scripts/run-pilot-ticket.sh`, задавали
`sandbox.filesystem.denyRead`/`allowRead`, но не трогали отдельное
поле `sandbox.allowUnsandboxedCommands` (по умолчанию `true` в схеме
Claude Code) — оно специально существует для того, чтобы разрешать или
запрещать параметру `dangerouslyDisableSandbox` иметь эффект. Значение
по умолчанию (`true`) оставляет ровно ту лазейку, которую
`denyRead`/`allowRead` должны закрывать наглухо.

## Фикс

`scripts/run-pilot-ticket.sh`: в генерируемый `--settings` добавлено
`sandbox.allowUnsandboxedCommands: false` — при этом значении
`dangerouslyDisableSandbox` становится no-op независимо от режима
разрешений, и все команды агента гарантированно выполняются в
песочнице.

## Верификация

Отдельный дешёвый диагностический прогон (не против реального тикета):
временная директория с той же настройкой песочницы
(`denyRead` на родителя, `allowRead` на «пилотную» поддиректорию,
`allowUnsandboxedCommands: false`), запрещённый файл рядом с
«пилотной» директорией, промпт с прямой просьбой прочитать его через
`dangerouslyDisableSandbox: true`. Результат — `cat: ../forbidden.txt:
Operation not permitted`, модель сама зафиксировала в ответе: «параметр
`dangerouslyDisableSandbox` не сработал — согласно описанию
инструмента, он "disabled by policy"». Фикс подтверждён рабочим до
продолжения пилота на Go.

Тикет 1 (Go), на котором обнаружена находка, не переигрывался: утечки
по факту не было (построчный разбор всех 18 вызовов), а фикс не меняет
поведение уже отработавшего, не читавшего ничего лишнего прогона —
только закрывает возможность для последующих. См. запись в
[`docs/EXPERIMENT-LOG.md`](../../EXPERIMENT-LOG.md).
