# Инцидент: контрактный гейт — дремлющая проверка, дрейф schemathesis, virtiofs-недетерминизм

Дата: 2026-08-31. Повод — решение пользователя включить контрактный тест
(Schemathesis по `docs/syncbox-openapi.yaml`) в цикл: за весь пилот
(тикеты 1–12, семь языков) он не запускался **ни разу**, хотя числится
одним из трёх acceptance-гейтов в `CLAUDE.md` («Метод», п. 3) и
`docs/SYNCBOX-SPEC.md` («Критерии приёмки»). Первый же прогон вскрыл три
переплетённые проблемы.

## 1. Дремлющий гейт нашёл реальный латентный баг сразу

Ретроактивный прогон `acceptance/contract-test.sh` против пост-тикет-7
состояния всех четырёх языков доклада — все четыре **упали**. Общий
корень (Python/JS/TS; Ruby не воспроизвёл, см. ниже):
`PUT /blobs/{key}` на состязательных значениях `key` (percent-encoded
байты, декодирующиеся в управляющие символы C1, символы дополнительных
плоскостей Unicode, высокие байты Latin-1, пустое тело) возвращал
**неперехваченный 500** вместо задокументированных 201/400 —
файловая операция записи блоба падала ошибкой уровня ОС (`EIO`,
`ENOENT` сразу после успешного с виду `write`, `OSError`/`errno 84
EILSEQ`), а обработчик отдавал общий 500. Эталонная реализация на тех же
входах отвечает 201.

Баг существовал с тикета 2 (happy-path PUT) / тикета 5 (traversal-валидация)
и не был пойман, потому что:

- **штатные тесты** модель пишет под свой же код — фаззить собственный
  PUT ключами с C1-байтами она не догадывается (та же слепая зона, что
  у кода);
- **acceptance-смок** — фиксированный happy-path сценарий, его
  единственная traversal-проверка структурная (`../evil.txt`,
  `%2e%2e%2fevil.txt`), экзотических байт не пробует;
- **контрактный тест** — property-based фаззинг, единственный гейт,
  достигающий этого класса входов, — не запускался.

Закрыто фикс-тикетом `ticket-12-fix-put500` (Python/JS/TS, см.
`docs/EXPERIMENT-LOG.md`). Ruby PUT-500 не имеет — 307/307 чисто.

**Вывод для эксперимента:** 21/21 канонический тикет «сошёлся» по
саморевью + юнит-тестам + happy-path смоку, но выключенный до сегодня
гейт поймал кросс-языковой контрактный дефект в первую же секунду
работы. Насколько сигнал «сошлось» зависит от того, какие проверки
активны, — стоит строкой в сравнительный отчёт.

## 2. schemathesis не был запинен; 4.x генерит метод QUERY → Ruby 501

Makefile ставил `schemathesis` без версии. На хосте оказался **4.24.3**,
тогда как `contract-test.sh` писался под CLI 3.x. В 4.x фаза coverage по
умолчанию генерит запросы неизвестными HTTP-методами (в т.ч. черновой
`QUERY`); Ruby отвечает на них **501** (эталон — 405), и проверка
`not_a_server_error` флагает 501 как серверную ошибку — хотя заголовок
самого `contract-test.sh` прямо декларирует, что реакцию на
unsupported-method он проверять **не должен**.

Из-за этого Ruby **выглядел** упавшим контракт (3 «падения», все —
QUERY-501) и едва не получил ненужный фикс-тикет по ложной посылке
(«проверка нашла баг, почини»). После сужения scope (см. фикс ниже)
Ruby проходит 307/307 — PUT-500 у него действительно нет, весь провал
был артефактом инструмента.

## 3. На macOS контрактный прогон недетерминирован (virtiofs)

Даже после сужения scope один и тот же вход, посланный дважды,
по-разному бьётся о bind-mount данных: Docker Desktop на macOS монтирует
`/data` через virtiofs/gRPC-FUSE, который недетерминированно отдаёт
I/O-ошибки на экзотических именах файлов. Замер 2026-08-31,
`--generation-deterministic`, 8 прогонов на язык:

| Язык       | pass/fail (bind-mount) | pass/fail (`/data` = tmpfs)                       |
| ---------- | ---------------------- | ------------------------------------------------- |
| JavaScript | 7/8                    | 8/8                                               |
| TypeScript | 7/8                    | 8/8                                               |
| Python     | 2/8                    | 4/8 (остаточный реальный граничный баг, не среда) |

Тот же класс, что уже описан в `docs/RUNBOOK.md` («На macOS падает
09-…») и `docs/PILOT-COMPARISON-all-languages.md` (штормовые ложные 404
на тикете 6 JS/TS).

## Что сделано

- **Пин версии:** `schemathesis==4.24.3` и `openapi-spec-validator==0.9.0`
  в Makefile (цель `venv`) — тем же принципом, что и точный ID модели:
  генератор не должен дрейфовать между прогонами.
- **Сужение scope:** `acceptance/schemathesis.toml` с
  `[phases.coverage] unexpected-methods = []` — полностью отключает
  подтест неизвестных методов, оставляя фаззинг `key` и проверку схемы.
  `contract-test.sh` вызывает schemathesis с `--config-file`.
- **Детерминизм на macOS:** контракт-гейт в `scripts/run-gates.sh`
  поднимает сервер с подсунутым `docker-compose.override.yml`, где
  `/data` — tmpfs (RAM, обычная Linux-fs), не bind-mount; плюс
  `--generation-deterministic` и прогон 3× (гейт зелёный только если
  зелены все три). smoke по-прежнему через реальные
  `run-server`/`run-client`.
- **Пассинг/фейл — по коду возврата schemathesis**, не по строке «No
  issues found» (warnings вроде «Missing test data» меняют итоговую
  строку, но не код).
- Строки тикетов 6–7 в `docs/EXPERIMENT-LOG.md` — контракт
  «провал зад. числом → пройден после 12-fix-put500» (Python/JS/TS) /
  «пройден, досчитано» (Ruby).

## Разрешение read-side (2026-09-01, по итогам обкатки авто-лупа `ticket-12-readside`)

Обкатка `scripts/run-pilot-loop.sh` на Python вскрыла, что остаточный
контракт-провал — **уровня спецификации, не кода**: `syncbox-openapi.yaml`
документировал `400` только для `PUT /blobs/{key}`, а `GET`/`DELETE`
на ключе, который Flask не может даже смаршрутизировать (декодируется в
`\n`), Python отдавал как `400` — вне схемы. Модель на 3-й итерации это
верно диагностировала, но починить не могла: копия схемы в `/workspace`
одноразовая, гейт проверяет каноническую.

Сделано:

- **Решение A** (выбор пользователя): в `docs/syncbox-openapi.yaml` и
  `docs/SYNCBOX-SPEC.md` добавлен `400` в ответы `GET`/`DELETE
  /blobs/{key}` — как уже было у `PUT`; с пометкой «реализация вправе
  вернуть `404` на тот же вход». Контракт стал пермиссивным
  (`GET` ∈ {200, 404, 400}); JS/TS/Ruby, отвечающие `404`, остаются
  валидны — перепроверено, регрессии нет.
- Код 3-й итерации лупа (`errorhandler(404)`→400 для unrouted `/blobs/*`,
  `blob_exists` / `send_file` / `unlink` в `try/except`) принят как
  корректное завершение read-side части, не покрытой
  `ticket-12-fix-put500`. Python contract-гейт с новой схемой + этим
  кодом — 3/3 зелёный.
- `parse-contract-failures.py` чинён: возвращал `[]` (первый заголовок
  секции FAILURES без ведущего `\n`) — из-за этого фикс-промпты 2–3
  итерации шли **без списка падений**.
- `build-fix-prompt.py`: не перечислять коды (брать из схемы), явный
  запрет править файлы контракта.
- `run-pilot-loop.sh`: детектор «агент правил `SYNCBOX-SPEC.md` /
  `syncbox-openapi.yaml`» — стоп с исходом «нужно решение оператора»,
  без трат оставшихся итераций.

## Read-side для TS/JS/Ruby (2026-09-01, авто-луп)

`ticket-12-readside` прогнан через `scripts/run-pilot-loop.sh` для
TypeScript, JavaScript, Ruby — **все три сошлись за 1 итерацию**
(contract 3/3). Это первая сходимость авто-лупа на реальном код-фиксе
(обкатка на Python показала только «крутится + корректно сдаётся»).

У всех трёх дыра оказалась того же класса, что PUT-500: `getBlob`/
`deleteBlob` ловили только `ENOENT`, любую другую ошибку ФС
(`EILSEQ`/`ENAMETOOLONG`/`EISDIR`, `SystemCallError` у Ruby)
перевыбрасывали → generic 500. JS/Ruby ранее проходили contract 3/3
только потому, что стохастический фаззер не попал в не-`ENOENT` сбой
в тот прогон. Фикс у всех: перехват расширен на любой сбой FS-вызова
чтения/удаления → 404; структурная валидация (`InvalidKeyError` → 400)
и PUT не тронуты. Сессии: TS `f64793d7` ($1.02), JS `a1ef7c17` ($1.00),
Ruby `a0e28dd9` ($2.43). Строки — в `docs/EXPERIMENT-LOG.md`.

Read-side всех четырёх языков доклада укреплён; contract-гейт — 3/3 на
всех (Python — по итогам обкатки + решения A, TS/JS/Ruby — этим прогоном).
