# Инцидент: `docker inspect` своего же контейнера раскрывает имя мета-репозитория

Дата обнаружения: 2026-08-26. Повод — рутинный скан транскрипта на
утечку контекста мета-репозитория (`OCaml`/`Scala`/`Golang`/«шест»/
`acceptance/smoke`/`acceptance/contract`/`reference-impl`/
`llm-lang-experiment`) после первого реального прогона пилота
TypeScript (тикет 1, `session_id` `3035088c-d307-4250-8b38-9f1615e1d464`).
Термин `llm-lang-experiment` дал 9 совпадений — первый случай, когда
этот скан вообще что-то нашёл на живом тикете с 2026-08-21 (Round 2,
Docker-обвязанный харнесс).

## Что обнаружено

Docker-out-of-Docker (`/var/run/docker.sock` хоста, проброшенный внутрь
контейнера харнеса — см.
[инцидент 2026-08-21](../2026-08-21-write-tool-sandbox-escape/README.md))
даёт агенту полноценный доступ к API демона хоста, а не только к
изолированной поддокеру песочнице. `docker inspect <container>` для
ЛЮБОГО контейнера, включая собственный контейнер харнеса, возвращает
от демона хоста реальные host-side пути bind-mount'ов (поле
`Source` в `.Mounts` / `.HostConfig.Binds`) — то, что видно демону,
не то, что видно файловой системе внутри контейнера. Файловая изоляция
(агент не может прочитать ничего вне `/workspace`) при этом не
нарушается — но агент **узнаёт**, куда именно смонтирован его
`/workspace` на хосте, включая полный путь и имя мета-репозитория.

## Причинная цепочка

Реконструирована по `transcript.jsonl` (все время — UTC):

1. `13:15:34.071` — агент выполняет рутинную проверку окружения
   `docker ps 2>&1 | head -20; docker info ...`. Вывод `docker ps`
   показывает единственный запущенный контейнер:
   `c5848ca9c838   pilot-harness:latest   ...   loving_meninsky` — это
   и есть собственный контейнер харнеса (других контейнеров в этот
   момент нет — чистка Docker-демона по префиксу `syncbox`/`workspace-`
   в `scripts/run-pilot-ticket.sh` перед каждым вызовом сработала как
   задумано).
2. `13:16:01.111` — отлаживая, почему `curl 127.0.0.1:<port>` не
   достучался до опубликованного порта (ожидаемое следствие
   вложенности контейнеров при Docker-out-of-Docker, не баг), агент
   запускает диагностику своего же контейнера:
   `docker inspect c5848ca9c838 --format '{{json .Mounts}}' ...;
   docker inspect c5848ca9c838 --format '{{json .HostConfig.Binds}}'; ...`.
3. `13:16:01.222` — демон хоста отвечает реальными host-side путями:

   ```json
   {"Type":"bind","Source":"<host-docker-sock>","Destination":"/var/run/docker.sock",...}
   {"Type":"bind","Source":"<claude-home-tmpdir>","Destination":"/home/node/.claude",...}
   {"Type":"bind","Source":"<pilot-host-dir>","Destination":"/workspace","Mode":"rw",...}
   ```

   Агент узнаёт: имя пользователя хоста (`paul`), структуру директорий
   (`~/work/...`), и буквальное имя мета-репозитория
   `llm-lang-experiment` — ровно то, что вся Docker-изоляция
   ([инцидент 2026-08-19](../2026-08-19-python-ticket1-contamination/README.md),
   [инцидент 2026-08-21](../2026-08-21-write-tool-sandbox-escape/README.md))
   должна была скрыть.
4. `13:21:17.819` — единственный раз агент **использует** узнанный путь:
   подставляет его в `--data-dir` для смок-проверки:
   `./run-server --data-dir <pilot-host-dir>/.smoke-data --port 8091`.
5. `13:21:18.846` — команда падает (`Exit 1`); в логе контейнера —
   `mkdir: cannot create directory '/Users': Permission denied`. Путь
   физически не существует внутри контейнера харнеса (примонтирован
   только `/workspace`, барьер файловой системы держит) — попытка
   использовать узнанное имя ни к чему не привела.
6. `13:21:2x` (следующие несколько шагов) — агент сам, без
   вмешательства, переключается на нейтральный путь внутри контейнера
   (`/tmp/syncbox-smoke-data`), сервер поднимается, `/healthz`
   проверяется через IP контейнера (`docker inspect
   syncbox-8091-server-1 --format '{{...IPAddress...}}'` — узкий
   формат, без `.Mounts`, без утечки). Итоговый самоотчёт агента
   объясняет поведение `127.0.0.1` технически (вложенный Docker,
   DooD) и не упоминает мета-репозиторий вообще.

## Аудит остальных прогонов

Все 16 архивных транскриптов (`docs/pilot-runs/*/*/*/transcript.jsonl`
— Python, Go, JavaScript канонические и superseded прогоны, плюс этот
тикет TypeScript) проверены на `llm-lang-experiment`: совпадения только
в этом одном. `docker inspect` как таковой — не редкость: использован
ещё в 6 других прогонах (Go тикет 2×2, Go тикет 3, JS тикет 2, JS тикет
3), но всегда с узким форматом (`{{.NetworkSettings.Networks...IPAddress}}`
или аналог) для получения IP/портов **compose-контейнера своего же
проекта** — ни разу не `.Mounts`/`.HostConfig.Binds`, ни разу не
собственный контейнер харнеса. Комбинация «широкий формат + инспекция
себя», давшая утечку, — уникальна для этого прогона.

## Оценка воздействия

- Файловый барьер не пробит: агент не мог и не пытался прочитать
  что-либо по узнанному пути (`<meta-repo-host-dir>/...`
  физически не существует внутри контейнера харнеса — подтверждено
  самим фактом падения шага 4 выше).
- Утекла строка (имя пользователя, структура директорий, имя
  мета-репозитория), не содержимое — ни `reference-impl`, ни
  `docs/pilot-runs/` с чужими реализациями агент не касался ни разу
  (скан по этим терминам — 0 совпадений, как и на всех прошлых
  прогонах).
- На итоговую реализацию тикета находка не повлияла: единственное
  использование узнанного пути закончилось ошибкой доступа, дальше
  агент действовал так, будто ничего не узнал.
- Тот же класс риска, что уже документирован и принят в
  `scripts/run-pilot-ticket.sh` (там — `docker images`/`docker ps`
  раскрывают чужие образы/контейнеры прошлых пилотов через общий
  демон), но конкретный вектор новый: не «чужие прогоны существуют»,
  а прямое узнавание имени и структуры самого мета-репозитория. Более
  идентифицирующая находка, чем прежде задокументированная, но по
  типу воздействия (агент видит факт, не получает доступ) —
  та же категория.

## Рассмотренные варианты фикса

Полностью закрыть канал без потери Docker-out-of-Docker нельзя: агенту
нужен `docker.sock` хоста, чтобы собирать и тестировать код тикета в
соседнем контейнере (см. «Docker-изоляция» в `SYNCBOX-SPEC.md`), а
любой процесс с доступом к `docker.sock` может запросить у демона
`inspect` на любой контейнер, включая себя — сам демон не различает
«свой» и «чужой» контейнер и не фильтрует поля ответа по тому, кто
спрашивает. Варианты, которые не выбраны:

- **Отдельный Docker-контекст/прокси перед сокетом**, фильтрующий
  `Mounts`/`HostConfig.Binds` из ответов `inspect` — отклонено:
  сложность, отдельный процесс-посредник, хрупкость к новым полям API
  демона, которые могут раскрывать то же самое (`docker exec`,
  `docker cp`, логи демона).
- **Переименовать директории пилотов так, чтобы host-путь не содержал
  узнаваемое имя** (например, монтировать через промежуточный симлинк
  с нейтральным именем) — отклонено как полумера: скрывает конкретно
  строку `llm-lang-experiment`, но не общий факт, что путь раскрывает
  структуру хоста и потенциально другие узнаваемые сегменты
  (`<host-path>`); не устраняет канал, только один конкретный
  текущий symptom.

## Что делаем

- Документируем как принятый остаточный риск архитектуры DooD — той же
  категории, что уже описана в `scripts/run-pilot-ticket.sh` для
  `docker images`/`docker ps`, теперь явно распространённой и на
  `docker inspect` с широким форматом. Комментарий в
  `scripts/run-pilot-ticket.sh` обновлён (см. коммит с этим
  инцидентом) — явно называет `docker inspect` вектором наравне с уже
  описанными.
- Термин `llm-lang-experiment` официально закрепляется в стандартном
  списке терминов для скана транскриптов на утечку контекста (уже
  использовался в части прошлых прогонов ситуативно — теперь
  обязателен для каждого прогона наравне с `OCaml`/`Scala`/`Golang`).

## Что не переигрывается

Тикет 1 пилота TypeScript **не аннулируется**: файловый барьер не
нарушен, узнанное имя не использовано ни в реализации, ни в решениях
агента, единственная попытка применить его провалилась и была
незамедлительно и самостоятельно обойдена. Точка данных валидна для
сравнения между языками. Все дальнейшие тикеты пилота (TypeScript
2–3 и последующие языки) продолжают на той же Docker-обвязанной
архитектуре — риск принят, не устранён, будет всплывать и дальше на
прогонах, где агент решит инспектировать собственный контейнер широким
форматом.
