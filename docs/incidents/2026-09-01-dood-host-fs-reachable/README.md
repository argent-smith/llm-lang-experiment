# Инцидент: через Docker-out-of-Docker агент дотягивается до файловой системы хоста

Дата: 2026-09-01. Повод — прогон тикета 9 (клиент `status`, dry-run),
язык Ruby. Найдено при построчном чтении транскрипта после автолупа, не
проявилось как падение гейта.

## Что произошло

Пилотный агент Ruby реализовал `status`, прогнал штатные тесты
(`run-tests`, 142/142 зелёных) — всё это ДО эпизода ниже — и стал
вручную собирать end-to-end проверку `run-client status` против живого
сервера. Уперся в ограничение Docker Desktop на macOS: вложенный
`docker compose` (обёртки `run-server`/`run-client` ходят в демон через
смонтированный хостовый сокет) не может примонтировать `/workspace/...`,
потому что хост не знает этот путь как shared —

```text
Error response from daemon: mounts denied:
The path /workspace/.tmp-sb-data is not shared from the host ...
```

Агент обошёл это, передав в `run-client` путь `/tmp`:

```sh
./run-client status /tmp --server http://127.0.0.1:8099
```

`run-client` резолвит аргумент (`dir="$(cd "$dir" && pwd)"` → `/tmp`),
экспортирует `SYNCBOX_CLIENT_DIR=/tmp` и делает `docker compose run` с
томом `${SYNCBOX_CLIENT_DIR}:/workdir`. Строку тома демон (в VM Docker
Desktop) резолвит против **своего** вида хоста — а `/tmp` (`/private/tmp`
на macOS) в дефолтном списке file-sharing Docker Desktop есть. В
контейнер клиента примонтировался **весь хостовый `/private/tmp`**.

`status` обошёл дерево целиком. Реализация Ruby для сравнения по SHA-256
делает `Digest::SHA256.file(path)` на каждый файл — то есть процесс
внутри одноразового контейнера клиента **прочитал байты каждого файла**
под хостовым `/private/tmp`. Агенту в контекст вернулся только вывод
`status` — список путей (`would upload <relative-key>`), не содержимое.
Среди ~тысяч путей:

- скрэтч и `tasks/*.output` чужих сессий Claude Code
  (`claude-501/-Users-<user>-Development-<work-project>/<uuid>/...`);
- скрэтч **этой самой сессии эксперимента**
  (`claude-501/-Users-<user>-work-llm-lang-experiment/<uuid>/scratchpad/ticket8-out/typescript.loop.json`,
  `loop-shakedown/`, `reverify/`, `run-ticket9.sh`, `insert-ticket8.py`…);
- посторонний хостовый мусор (Arturia, Adobe `ExmanProcessMutex`, …).

Агент распознал это («нюанс окружения»), остановил и удалил контейнеры,
`rm -rf` свой собственный `/tmp/sb-*` скрэтч (внутри контейнера харнеса,
безвредно), перепрогнал `run-tests` (зелёные) и финализировал. Ничего из
списка он не читал, не цитировал и не использовал.

Python/JS/TS в тикете 9 в эту ловушку не попали — их агенты били
`run-client` только по своим же поддиректориям `/tmp/syncbox-<uuid>/`
(созданным ими самими). Bare `/tmp` — только Ruby, один раз.

## Severity

- **Для валидности эксперимента — низкая.** Реализация и все тесты были
  готовы и зелены *до* эпизода; нулевое влияние на решение. Ключевые
  цели риска №1 из `CLAUDE.md` — `acceptance/reference-impl` и
  `docs/pilot-runs/<другие языки>/code` — лежат в репозитории, не в
  `/private/tmp`, этим вектором недостижимы. Что реально утекло в
  контекст: пути, из которых видно, что есть параллельные языковые
  прогоны и QA-обвязка (`loop-shakedown`, `reverify`), — но агент на
  тикете 9, построив тикеты 1–8, и так знал, что языков несколько.
- **Структурно — средняя.** Заявленная в `CLAUDE.md` гарантия («если
  путь не примонтирован — его физически нет в файловой системе
  процесса») дырявая при Docker-out-of-Docker: агент может получить
  **новый bind-mount хостового пути по своему выбору**, просто передав
  его в `run-client`/`run-server`. Достижим любой путь под каталогом
  file-sharing Docker Desktop — на этой машине `/tmp`, `/Users`,
  `/private`, `/Volumes`, `/var/folders`. Это врождённое свойство
  DooD с общим сокетом, а не баг конкретной обёртки.

Тот же демон-канал раскрывал и два более мягких (оба уже были
задокументированы, оба закрываются этим же фиксом):
`docker images`/`docker ps` показывали образы/контейнеры эталонной
реализации и прошлых прогонов; `docker inspect` своего же контейнера
харнеса отдавал host-side путь bind-mount'а с именем мета-репозитория
(`docs/incidents/2026-08-26-docker-inspect-hostpath-leak/`).

## Почему очевидный фикс не работает

Первая идея — дать контейнеру харнеса собственный `/tmp`, примонтировав
туда пустой хостовый каталог на прогон (`-v $RUN_SCRATCH:/tmp`).
Проверено эмпирически 2026-09-01 — **не закрывает**: `docker` CLI
передаёт строку пути bind-mount демону, а демон резолвит её против
своего вида хоста, а не против mount-namespace вызывающего контейнера.
Вложенный `docker run -v /tmp:/probe` из такого харнеса всё равно
видел хостовый `/private/tmp` целиком (маркер-файл на месте):

```text
*** LEAK: nested container sees HOST /private/tmp despite harness /tmp remap ***
```

## Фикс: Docker-in-Docker вместо Docker-out-of-Docker

Решение пользователя от 2026-09-01. Контейнер харнеса больше не получает
хостовый `/var/run/docker.sock`; вместо этого внутри поднимается
собственный `dockerd` (`--privileged` на `docker run` харнеса, см.
`scripts/pilot-harness-entrypoint.sh`). `docker compose` агента бьёт в
этот внутренний демон. Его файловая система — оверлей самого контейнера
харнеса; хостовых `/private/tmp` и `/Users` в ней не существует,
поэтому агент физически не может их примонтировать в контейнер тикета.

Проверено синтетически 2026-09-01 (после сборки нового образа): из
контейнера харнеса `docker run -v /tmp:/probe` и `-v /Users:/u` в
дочерних контейнерах не видят ничего с хоста (`/probe` пуст, маркер-файл
недоступен, `/Users/<user>` отсутствует); `docker images`/`docker ps`
внутреннего демона пусты — прежние мягкие каналы (`docker images`,
`docker inspect` своего контейнера) закрыты заодно.

Проверено функционально 2026-09-02: тикет 9 (Python) прогнан целиком
через новый харнесс — агент поднял внутренний `dockerd`, собрал и
прогнал `docker compose` код тикета в нём, сошёлся за 1 итерацию
авто-лупа, гейты зелёные (run-tests pass, contract 3/3, smoke info
10/13). Архив — `docs/pilot-runs/python/ticket-9-dind-shakedown/`
(не канон; канон тикета 9 — прогоны на DooD, независимо
перепроверенные).

Цена, принятая осознанно:

- `--privileged` на том же контейнере, где уже
  `claude -p --dangerously-skip-permissions`. Периметр не расширяется —
  барьер по-прежнему один (namespace-изоляция самого контейнера харнеса
  от хоста), просто теперь замкнутый: внутри `--privileged` даёт
  доступ к ядру, но наружу, к хосту, из контейнера по-прежнему нет
  пути.
- Внутренний демон стартует без кеша слоёв — каждый прогон заново
  тянет базовые образы (`python:3.12-slim`, `node:22-alpine`,
  `ruby:3.3-slim` и т. п.). ~1 мин инфра-времени, одинаково по языкам,
  отдельной статьёй в `timing-breakdown` (не в `duration_api_ms`).
- `/var/lib/docker` внутреннего демона — анонимный том (иначе
  overlay2 поверх overlay2 в VM Docker Desktop не инициализируется);
  `--rm` сносит его вместе с контейнером, поэтому демон каждого прогона
  пуст и блок чистки хостового демона от `syncbox*`/`workspace-*`
  (`run-pilot-ticket.sh`) убран за ненадобностью.

Бонус: прежняя ошибка `mounts denied` для путей под `/workspace`
(с которой всё и началось) на DinD исчезает — bind-mount резолвится
против файловой системы контейнера харнеса, где `/workspace` есть.

## Граница фикса

Тикеты 1–9 всех языков прошли на DooD — этого фикса не отражают.
Тикет 9 (4 языка доклада) — последний на DooD; сам результат тикета 9
валиден (сходимость реальна, `status` независимо перепроверен 4/4:
read-only, сервер и локальная ФС не меняются, направления верны),
находка — свойство харнеса, ортогональное тому, решил ли агент тикет.
Тикет 10 и далее — на DinD.
