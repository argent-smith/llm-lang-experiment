# CLAUDE.md — эксперимент к докладу RubyRussia 2026

Передача дела из Cowork в Claude Code. Дальше — запуск и ведение самого эксперимента.

## Контекст

Готовится эмпирическая часть доклада на RubyRussia 2026 (CFP до 1 сентября 2026, конференция 2 октября 2026, Москва). Рабочее название: **«На вкус и цвет все фломастеры разные. Особенно если вы пишете на Ruby»**.

Приложены два артефакта — прочитать перед началом работы:

- `Конспект разговора с ментором.md` — расшифровка и конспект исходного разговора, из которого выросла тема. В нём же — вторая тема, Loop Engineering, отложенная до весны/лета 2027. Этот эксперимент её не касается.
- `CFP RubyRussia 2026.md` — текущий текст заявки: гипотеза, метод, тезисы, аудитория. В публичном тексте харнесс и модель намеренно не названы («фиксированная связка модель — харнесс») — здесь, для работы, они называются прямо.

## Гипотеза

ИИ-агенты неравнодушны к языку программирования не из-за качеств языка, а из-за объёма его кода в обучающей выборке модели. Два независимых механизма:

1. Python в фаворе, потому что это язык выбора самих авторов LLM.
2. JS/TypeScript в фаворе просто по массовости, безотносительно того, кто пишет модели.

Ruby не подпадает ни под одну из причин и по обеим должен проигрывать. Вопрос — оправдан ли этот прогноз статистически, а не только на анекдотах.

## Полигон (зафиксировано)

- **Харнесс:** Replit Agent
- **Модель:** Claude Sonnet
- **Переменная:** язык проекта. Всё остальное держим постоянным.
- **Языки доклада:** Python, JS/TS, Ruby — только эти три идут в CFP и в сам доклад RubyRussia 2026.
- **Языки вне доклада:** OCaml, Scala, Golang — добавлены дополнительно. В доклад RubyRussia 2026 не идут, данные собираются про запас для других исследований.

Цель — не починить проблему, а измерить, есть ли статистически значимый эффект языка на то, как агент справляется с тикетами. Как чинить (если подтвердится) — тема другого доклада, сюда не лезем.

## Проект: Syncbox

Вместо готового опенсорс-проекта — единая спецификация, реализуемая с
нуля отдельно на каждом из шести языков: [SYNCBOX-SPEC.md](SYNCBOX-SPEC.md).
HTTP API и CLI зафиксированы буквально одинаково для всех языков, внутреннее
устройство — свободное. Причина смены подхода (было: брать готовый реальный
опенсорс-проект) — два довода одновременно:

1. Сопоставимость. Реальных прикладных проектов одинакового масштаба и
   сложности на всех шести языках (включая OCaml и Scala) просто не
   существует — без общей спецификации разницу в тикетах спишут на
   несопоставимость проектов, а не на язык.
2. Утечка обучающих данных. Если проект уже существует и популярен,
   модель могла запомнить конкретные фиксы к его issues — тогда
   измеряется не общий объём кода на языке в обучающей выборке (это и
   есть гипотеза), а конкретно эта репутация конкретного репозитория.
   Проект с нуля снимает этот confound.

## Метод

Одинаков для всех языков — и для тех, что идут в доклад, и для тех, что вне его. Доклад определяет только то, какие данные попадут в презентацию, а не то, как их собирают.

Для каждого языка:

1. Создать пустой проект по спецификации Syncbox — с нуля, без готового кода.
2. Импортировать в Replit, подключить Claude Sonnet.
3. Прогнать через тикеты (стартовый бэклог — в SYNCBOX-SPEC.md) в цикле: реализация → саморевью на критические замечания → фикс → повторное ревью → повтор до сходимости или явного отказа.
4. Зафиксировать на каждый тикет: число итераций до исхода, время, токены (если Replit их отдаёт), плюс отдельно — кейсы провала (зацикливание, повторяющиеся ошибки).

## Сначала пилот (2–3 тикета на язык), потом масштаб

Пилот проходит по всем шести языкам — открытые риски методики одинаковы независимо от того, идёт язык в доклад или нет. Три вещи не проверены и могут сломать методику, если пропустить:

1. Фиксируется ли версия Claude Sonnet на весь эксперимент, или Replit может незаметно подменить её более новой версией посреди прогона.
2. Отдаёт ли Replit реальные цифры по токенам и времени на задачу, или чекпоинты агента — это про откат состояния, а не про измерения; тогда трекать придётся отдельно (API/ручной лог).
3. Насколько шесть реализаций фактически остаются в рамках спецификации Syncbox — если агент на одном языке достраивает сверх неё, а на другом следует буквально, тикеты перестают быть сравнимыми, несмотря на общую спецификацию.

Полный прогон (10–100 тикетов на язык) имеет смысл начинать только после того, как пилот закрыл все три пункта — для каждого языка, который в нём участвует.

## Лог

Вести по каждому тикету: язык / проект / тикет / в докладе (да/нет) / число итераций / время / токены / исход (сошлось / сдалось) / заметки по кейсам провала. Формат — на усмотрение Claude Code, важна полнота полей.

Поле «в докладе» отделяет данные по Python/JS/Ruby (идут в RubyRussia 2026) от данных по OCaml/Scala/Golang (собираются про запас, для других исследований) — важно не смешивать при анализе и выводах.

## Не делать

- Не переключаться на решение проблемы (Loop Engineering) — это отдельный доклад.
- Не отклоняться от SYNCBOX-SPEC.md между языками — HTTP API и CLI зафиксированы буквально одинаково для всех шести; расхождение делает тикеты несравнимыми (см. пункт 3 в разделе «Сначала пилот»).
- Не подавать промежуточные результаты как доказанные выводы — CFP прямо обещает гипотезу и первые наблюдения к октябрю, не готовые выводы.
- Не подавать данные и выводы по OCaml/Scala/Golang как часть доклада RubyRussia 2026 — эти языки вне CFP, данные копятся для другого материала.
