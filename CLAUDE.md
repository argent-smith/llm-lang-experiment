# CLAUDE.md — эксперимент к докладу RubyRussia 2026

Передача дела из Cowork в Claude Code. Дальше — запуск и ведение самого эксперимента.

## Контекст

Готовится эмпирическая часть доклада на RubyRussia 2026 (CFP до 1 сентября 2026, конференция 2 октября 2026, Москва). Рабочее название: **«На вкус и цвет все фломастеры разные. Особенно если вы пишете на Ruby»**.

Приложен артефакт — прочитать перед началом работы:

- `docs/CFP RubyRussia 2026.md` — текущий текст заявки: гипотеза, метод, тезисы, аудитория. В публичном тексте харнесс и модель намеренно не названы («фиксированная связка модель — харнесс») — здесь, для работы, они называются прямо.

## Гипотеза

ИИ-агенты неравнодушны к языку программирования не из-за качеств языка, а из-за объёма его кода в обучающей выборке модели. Два независимых механизма:

1. Python в фаворе, потому что это язык выбора самих авторов LLM.
2. JavaScript и TypeScript в фаворе просто по массовости, безотносительно того, кто пишет модели — это один и тот же механизм для обоих, но в эксперименте они идут как два самостоятельных языка (см. «Полигон» ниже), не один слот на двоих.

Ruby не подпадает ни под одну из причин и по обеим должен проигрывать. Вопрос — оправдан ли этот прогноз статистически, а не только на анекдотах.

## Полигон (зафиксировано)

- **Харнесс:** Claude Code — headless-режим (`claude -p`) или Agent SDK, локально/скриптом. Не Replit Agent: тот работает только через браузер, цикл тикетов не автоматизировать — проверено отдельным исследованием, а не предположено.
- **Модель:** Claude Sonnet, точный ID (`claude-sonnet-5`) передаётся явно на каждый вызов — у Anthropic ID модели это зафиксированный снепшот, не алиас, сам по себе не дрейфует.
- **Переменная:** язык проекта. Всё остальное держим постоянным.
- **Языки доклада:** Python, JavaScript, TypeScript, Ruby — только эти четыре идут в CFP и в сам доклад RubyRussia 2026. JavaScript и TypeScript — с 2026-08-25 два самостоятельных языка эксперимента (свой пилот, свой лог), не один комбинированный слот «JS/TS», как было изначально.
- **Языки вне доклада:** OCaml, Scala, Golang — добавлены дополнительно. В доклад RubyRussia 2026 не идут, данные собираются про запас для других исследований.

Цель — не починить проблему, а измерить, есть ли статистически значимый эффект языка на то, как агент справляется с тикетами. Как чинить (если подтвердится) — тема другого доклада, сюда не лезем.

## Проект: Syncbox

Вместо готового опенсорс-проекта — единая спецификация, реализуемая с
нуля отдельно на каждом из семи языков: [docs/SYNCBOX-SPEC.md](docs/SYNCBOX-SPEC.md).
HTTP API и CLI зафиксированы буквально одинаково для всех языков, внутреннее
устройство — свободное. Причина смены подхода (было: брать готовый реальный
опенсорс-проект) — два довода одновременно:

1. Сопоставимость. Реальных прикладных проектов одинакового масштаба и
   сложности на всех семи языках (включая OCaml и Scala) просто не
   существует — без общей спецификации разницу в тикетах спишут на
   несопоставимость проектов, а не на язык.
2. Утечка обучающих данных. Если проект уже существует и популярен,
   модель могла запомнить конкретные фиксы к его issues — тогда
   измеряется не общий объём кода на языке в обучающей выборке (это и
   есть гипотеза), а конкретно эта репутация конкретного репозитория.
   Проект с нуля снимает этот confound.

## Метод

Одинаков для всех языков — и для тех, что идут в доклад, и для тех, что вне его. Доклад определяет только то, какие данные попадут в презентацию, а не то, как их собирают.

Для каждого языка:

1. Создать пустой проект по спецификации Syncbox — с нуля, без готового кода.
2. Прогнать через Claude Code headless (`claude -p --model claude-sonnet-5 --effort xhigh --safe-mode --dangerously-skip-permissions --output-format json ...` либо эквивалент через Agent SDK) — не `--bare`: в этом окружении он требует `ANTHROPIC_API_KEY` и ломает OAuth-аутентификацию, `--safe-mode` даёт то же отключение CLAUDE.md/хуков/скиллов/плагинов мета-репозитория без этого требования (проверено эмпирически на реальном прогоне, не только по `--help`). Сам вызов `claude -p` идёт не на хосте, а внутри Docker-контейнера харнеса (`scripts/pilot-harness.Dockerfile` + `scripts/pilot-harness-entrypoint.sh`, запускается через `scripts/run-pilot-ticket.sh`), где с хоста смонтирована только директория пилота (`/workspace`). Сборка/тестирование кода тикета идёт в отдельном контейнере через Docker-in-Docker: внутри харнеса поднимается собственный `dockerd` (`--privileged`), `docker compose` агента бьёт в него, а не в хостовый демон. С 2026-09-01 это заменило Docker-out-of-Docker (проброс хостового `/var/run/docker.sock`): на DooD агент мог получить bind-mount любого хостового пути под каталогом file-sharing Docker Desktop, просто передав его в `run-client`/`run-server` — `run-client status /tmp` примонтировал хостовый `/private/tmp` целиком (найдено на тикете 9, Ruby — [docs/incidents/2026-09-01-dood-host-fs-reachable/](docs/incidents/2026-09-01-dood-host-fs-reachable/README.md)). У внутреннего демона DinD хостовых `/private/tmp` и `/Users` в файловой системе нет, плюс он пуст на старте каждого прогона (`/var/lib/docker` — анонимный том, `--rm` его сносит), что заодно закрыло прежние мягкие каналы через `docker images`/`docker ps`/`docker inspect` своего контейнера. Базовые образы языковых стендов (`python:3.12-slim`, `node:22-alpine`, `ruby:3.3-slim`, `alpine`) предзапечены в образ харнеса (`scripts/build-base-images-tar.sh` → `base-images.tar` → `docker load` во вложенном демоне на старте) — иначе `pull` базы попадал бы во время каждого прогона; entrypoint через EXIT-trap копирует транскрипт сессии на `/workspace` и делает `sync` до `--rm`-teardown (без этого архивный транскрипт под DinD обрезался — [docs/incidents/2026-09-02-dind-timing-broken/](docs/incidents/2026-09-02-dind-timing-broken/README.md)). Ещё раньше эта Docker-обвязка заменила схему с `sandbox.filesystem.denyRead`/`allowRead` через `--settings`: аудит 2026-08-21 показал, что она ограничивала только Bash-подпроцессы, а инструменты Read и Write агента её не соблюдали вообще (Read — управляется только системой разрешений, которую `--dangerously-skip-permissions` отключает; Write не поддерживает ограничение по пути ни в каком режиме) — см. разбор в [docs/incidents/2026-08-21-write-tool-sandbox-escape/](docs/incidents/2026-08-21-write-tool-sandbox-escape/README.md). Внешняя, обеспечиваемая ядром ОС изоляция контейнера — единственный барьер, который агент не может обойти изнутри: если путь не примонтирован, его физически нет в файловой системе процесса. Весь код тикета (сервер и клиент), который пишет и тестирует агент, тоже выполняется только в Docker-контейнере, не напрямую в контейнере харнеса — обязательное условие для всех «стендов» эксперимента, см. раздел «Docker-изоляция» в `docs/SYNCBOX-SPEC.md`. Известный, принятый как есть побочный эффект headless-режима: каждый вызов несёт небольшое сопутствующее использование `claude-haiku-4-5` (~1500 токенов, ~$0.0015 — видно в поле `modelUsage` результата, отдельно от основного `usage`), устранить его без перехода на `--bare` (который ломает OAuth) не удалось — не искажает сравнение между языками (одинаково на каждом вызове), но формально каждый прогон не «только claude-sonnet-5».
3. Прогнать через тикеты (стартовый бэклог — в `docs/SYNCBOX-SPEC.md`) в цикле: реализация → саморевью на критические замечания + штатные тесты проекта + внешний acceptance-смок + контрактный тест (Schemathesis по `docs/syncbox-openapi.yaml`) → фикс → повторное ревью → повтор до сходимости или явного отказа. Штатные тесты, смок и контрактный тест — часть критерия «сошлось/сдалось» наравне с саморевью, не постфактум-проверка. Сами скрипты (`acceptance/smoke.sh`, `acceptance/contract-test.sh`) и эталонная реализация — только в этом мета-репозитории, не копируются и не упоминаются по путям в текстах, которые видит пилотный агент (см. пункт 2 и разбор инцидента выше). С 2026-08-20 обязательность штатных тестов на каждый тикет закреплена прямо в тексте `docs/SYNCBOX-SPEC.md` (раздел «Критерии приёмки») — раньше это было только нашим критерием оценки, а пилотный агент прямого указания писать тесты не получал (Python не писал ни разу на трёх тикетах, Go писал на всех трёх без указания — см. `docs/PILOT-COMPARISON-python-go.md`). Пилоты Python и Go прошли до этого изменения — не отражают его.

   **С 2026-08-31 (тикет 8 языков доклада и далее) цикл скриптован, не ручной.** `scripts/run-pilot-loop.sh` на каждой итерации: `claude -p` → `scripts/run-gates.sh` (три гейта — `run-tests` реализации, `acceptance/smoke.sh`, `acceptance/contract-test.sh` через Schemathesis) → при провале блокирующего гейта авто-строит path-free промпт-симптом (`scripts/build-fix-prompt.py`: вырезает пути хоста, имена acceptance-скриптов, «schemathesis», порт) для следующего `claude -p` — до сходимости всех блокирующих гейтов или `--max-iters` (по умолчанию 4). Режимы гейтов: contract — block, smoke — info (пока не сделаны тикеты 8–11: шаги 08–11 смока падают by design), tests — block. Каждая итерация — отдельный вызов `run-pilot-ticket.sh`, отдельная запись в `docs/pilot-runs/` и отдельная строка в журнале; сводка по итерациям — `<out>.loop.json`. До этой правки (тикеты 1–12) гейты гонял оператор вручную между вызовами, и многовызовный цикл ревью→фикс сработал по существу лишь трижды за весь пилот (тикет 7 Python/JS — bash-баг `run-client`; тикет 12-fix-put500 Python/JS/TS — PUT-500). Данные тикетов 1–12 отражают прежний, ручной метод — не смешивать.

   **Контракт-гейт детерминирован через tmpfs.** `run-gates.sh` поднимает сервер с подсунутым `docker-compose.override.yml`, где `/data` — tmpfs, не bind-mount с хоста: на macOS bind-mount данных идёт через virtiofs Docker Desktop, недетерминированно отдающий I/O-ошибки на экзотических именах файлов — из-за этого сырой контракт-прогон флапал 2–7 падений из 8 на идентичном входе (замерено 2026-08-31). Плюс `--generation-deterministic` и прогон 3× (гейт зелёный только если зелены все три — один язык, Python, всё равно флапает ~4/8 на реальном граничном ключе). smoke по-прежнему идёт через реальные `run-server`/`run-client` — ему нужен полный стенд. Schemathesis закреплён точной версией (`schemathesis==4.24.3` в Makefile) — тем же принципом, что и точный ID модели.

   **Конвенция `run-tests`** (SYNCBOX-SPEC.md, «Критерии приёмки») — обязательная обёртка, гоняет штатные тесты реализации в Docker, как `run-server`/`run-client`. Агент пишет её с тикета 8+; для пилотов тикетов 1–12 (py/js/ts/ruby) обёртки дописаны руками под гейт.
4. Code security пробовали (bandit для Python, gosec для Go, 2026-08-20) и убрали: сравнение находок между языками оказалось неинформативно для гипотезы эксперимента — числа отражали в первую очередь разное покрытие правил между инструментами разных языков (`bandit` не ловит path traversal из коробки, `gosec` ловит), не разницу в безопасности кода. Разбор — `docs/PILOT-COMPARISON-python-go.md`, раздел «Code security (исключено)».
5. Зафиксировать на каждый тикет: число итераций до исхода, время, токены — точно, из `usage` в JSON-выводе Claude Code (`--output-format json`), а не оценка задним числом; плюс отдельно — кейсы провала (зацикливание, повторяющиеся ошибки).

### CI-проверки

| Проверка              | Пример инструмента                                                | Кормит цикл ревью? |
| --------------------- | ----------------------------------------------------------------- | ------------------ |
| Штатные тесты проекта | RSpec, pytest, Jest/Vitest, `go test`, `sbt test`, `dune test`    | Да                 |
| Acceptance-смок       | `acceptance/smoke.sh` в этом репозитории, чёрный ящик по HTTP/CLI | Да                 |

Штатные тесты, acceptance-смок и контрактный тест — часть критериев «сошлось/сдалось»: их результат учитывается в самом цикле «реализация → саморевью → фикс → повторное ревью» наравне с саморевью модели, а не только постфактум. Code security не входит в эту таблицу — решение отвергнуто по итогам пилота Python/Go (см. пункт 4 выше).

## Сначала пилот (2–3 тикета на язык), потом масштаб

Пилот проходит по всем семи языкам — открытые риски методики одинаковы независимо от того, идёт язык в доклад или нет. Смена харнесса (Replit Agent → Claude Code) закрыла по конструкции два из трёх прежних рисков: точная фиксация модели и точные цифры по токенам теперь не гипотеза о поведении чужого сервиса, а прямой результат того, как мы сами вызываем CLI/SDK. Остаются:

1. Не просачивается ли контекст этого мета-репозитория (CLAUDE.md, `.claude/settings.json`, хуки, содержимое `acceptance/reference-impl`, `docs/pilot-runs/` с уже сошедшимися реализациями других языков) в изолированный прогон. Закрыто в два раунда. Раунд 1 (2026-08-19): первый реальный прогон (тикет 1, Python) показал 100%-воспроизводимую утечку через обычные Bash/Read — агент нашёл и почти дословно скопировал `acceptance/reference-impl` (разбор — [docs/incidents/2026-08-19-python-ticket1-contamination/](docs/incidents/2026-08-19-python-ticket1-contamination/README.md)); фикс — текст `SYNCBOX-SPEC.md` больше не называет и не описывает пути внутри мета-репозитория, плюс файловая песочница `sandbox.filesystem.denyRead`/`allowRead` через `--settings`. Раунд 2 (2026-08-21): аудит показал, что песочница раунда 1 ограничивала только Bash-подпроцессы — инструменты Read и Write агента её не соблюдали вообще (построчный аудит всех 6 состоявшихся на тот момент прогонов подтвердил, что эксплуатации не было, но структурная гарантия была иллюзорной) — разбор и фикс (весь вызов `claude -p` обёрнут в Docker-контейнер с единственной примонтированной директорией пилота) в [docs/incidents/2026-08-21-write-tool-sandbox-escape/](docs/incidents/2026-08-21-write-tool-sandbox-escape/README.md). Раунд 3 (2026-09-01): прогон тикета 9 (Ruby) вскрыл, что Docker-обвязка раунда 2 держала файловый барьер, но не покрывала хостовый Docker-демон — через проброшенный сокет (Docker-out-of-Docker) агент мог примонтировать любой хостовый путь под каталогом file-sharing Docker Desktop, передав его в `run-client`/`run-server`; `run-client status /tmp` обошёл весь хостовый `/private/tmp` (включая скрэтч чужих сессий и этого же эксперимента). Эксплуатации-влияния на результат не было (реализация и тесты были готовы и зелены до эпизода, агент распознал и отбросил), но структурная гарантия снова оказалась дырявой. Фикс — переход на Docker-in-Docker (внутренний `dockerd`, у которого хостовой ФС в принципе нет), [docs/incidents/2026-09-01-dood-host-fs-reachable/](docs/incidents/2026-09-01-dood-host-fs-reachable/README.md). Все три раунда подтверждены диагностическими прогонами; для раундов 2–3 остаётся накопить то же на реальных тикетах пилота (не только на синтетической проверке), по мере того как пилот продолжается. Тикеты 1–9 прошли на DooD, тикет 10 и далее — на DinD.
2. Насколько семь реализаций фактически остаются в рамках спецификации Syncbox — если агент на одном языке достраивает сверх неё, а на другом следует буквально, тикеты перестают быть сравнимыми, несмотря на общую спецификацию.
3. Устойчивость самого цикла при скриптованном запуске — не упирается ли частая последовательность вызовов (`-p` → `--resume` → `-p` → ...) в рейт-лимиты, и если да, как пауза на бэкофф отражается в логе, чтобы не исказить число итераций/время. Первый живой сигнал получен 2026-08-24: один вызов пилота (Go, тикет 2, переигровка на Docker-харнессе) упал `429 session limit` (`api_error_status: 429`, `terminal_reason: api_error`) с точным временем сброса в самом ответе API (`resets 5:30pm (UTC)`) — не хаотичный рейт-лимит на уровне запросов, а фиксированный оконный лимит использования, ждать backoff бессмысленно, только явную паузу до времени сброса. Прогон просто повторён после сброса тем же вызовом `scripts/run-pilot-ticket.sh` — само по себе воспроизводимо, не потребовало отдельного фикса харнеса. Полноценного стресс-теста цикла `--resume` это по-прежнему не даёт (сошёлся с первой попытки после паузы), но подтверждает: сигнал рейт-лимита в `--output-format json` структурирован и легко парсится (`is_error`, `api_error_status`, `result`), а не требует догадок по формату stderr.

4. Публичность репозитория. Репозиторий публичный: эталонная реализация (`acceptance/reference-impl`), acceptance-скрипты, спецификация и полные решения прошлых прогонов (`docs/pilot-runs/*/*/*/code`) доступны всем, в том числе агенту. На 44 завершённых прогона это не влияет — они шли при приватном репозитории, — но харнесс сейчас не запрещает веб: `claude -p` в контейнере с `--dangerously-skip-permissions` может обратиться к GitHub через `WebFetch` или `curl`. До полного прогона закрыть веб-доступ агента: `--disallowedTools WebFetch,WebSearch` в вызове `claude -p` (`scripts/run-pilot-ticket.sh`) и ограничение исходящей сети контейнера (сборке кода тикета нужен доступ к реестрам пакетов, значит, нужен allowlist хостов), затем проверить диагностическим прогоном по образцу трёх раундов из пункта 1. Пока это не сделано, полный прогон не запускать: запуск `scripts/run-pilot-*.sh` заблокирован гардом (`scripts/lib-open-web-guard.sh`) и требует явного `PILOT_ACK_OPEN_WEB=1`, которое годится только для отладки харнеса. После закрытия веба гард удалить.

Полный прогон (10–100 тикетов на язык) имеет смысл начинать только после того, как пилот закрыл все четыре пункта — для каждого языка, который в нём участвует.

## Лог

Вести по каждому тикету: язык / проект / тикет / в докладе (да/нет) / число итераций / время / токены / исход (сошлось / сдалось) / штатные тесты (прошли/нет) / acceptance-смок (прошёл/нет) / контрактный тест (прошёл/нет) / заметки по кейсам провала. Формат — на усмотрение Claude Code, важна полнота полей.

Поле «в докладе» отделяет данные по Python/JS/Ruby (идут в RubyRussia 2026) от данных по OCaml/Scala/Golang (собираются про запас, для других исследований) — важно не смешивать при анализе и выводах.

Штатные тесты, acceptance-смок и контрактный тест влияют на «исход» — участвуют в решении, сошёлся тикет или нет. Code security не собирается — решение отвергнуто по итогам пилота Python/Go, см. раздел «Метод».

Поле «время» — это `duration_ms` из `--output-format json` конкретного вызова `claude -p` (переведённое в минуты), не календарное время работы над тикетом. Оно покрывает весь этот один вызов целиком — включая локальное выполнение инструментов внутри него (сборка Docker-образа, тесты, curl), не только генерацию модели — но не включает и не может включать паузы между отдельными вызовами `claude -p` в рамках одного тикета (переигровки после находок, ожидание решений человека, правку харнеса) — headless-вызов под `--dangerously-skip-permissions` не имеет точки, где мог бы остановиться и ждать кого-то. При нескольких попытках на один тикет (переигровки, «сдался») сумма «время» по всем строкам с этим тикетом — это сумма времени модели по отдельным вызовам, не календарное время до итогового исхода.

Отдельное поле «Время (API/инфра/работа)» в журнале — попытка разделить эту сумму на составляющие, а не только назвать проблему: `duration_api_ms` (реальное имя поля в `result.json`, не `duration_ms_api`, как можно было бы предположить по аналогии) — время именно на вызовы модели, уже готовое поле Claude Code; «инфра» (холодная загрузка Docker-образов/установка зависимостей) и «работа» (тесты, компиляция написанного агентом кода, отладка) — досчитаны по `transcript.jsonl` эвристическим классификатором `scripts/analyze-timing-breakdown.py`. Посчитано ретроактивно для 21 канонического тикета пилота (2026-08-28) — см. `docs/EXPERIMENT-LOG.md` и `docs/PILOT-COMPARISON-all-languages.md`; для будущих тикетов пересчитывается автоматически как часть `scripts/run-pilot-ticket.sh`.

С переходом на Docker-in-Docker (тикет 10) метрика сломалась: (1) архивный `transcript.jsonl` обрезался при мгновенном teardown контейнера (`--rm` + claude как PID 1 через `exec`) — у Python тикета 10 он охватывал ~12% времени прогона, docker-команды агента отсутствовали, классификатору нечего разбирать; (2) `duration_ms` под вложенным демоном недосчитывает (старт `dockerd` до запуска claude выпадает из self-таймера), а `duration_api_ms` завышен — на контрольном прогоне он на 15 с больше всего времени жизни контейнера (сумма по турнам, перекрывается стримингом/очередью). Прежняя разбивка (`work = duration_ms − duration_api_ms − инфра`) уходила в минус. Фикс 2026-09-02: `scripts/run-pilot-ticket.sh` меряет внешний `container_wall_ms` вокруг `docker run` (в `harness-timing.json`); `scripts/pilot-harness-entrypoint.sh` через EXIT-trap копирует транскрипт на `/workspace` и делает `sync` до teardown; `analyze-timing-breakdown.py` больше не опирается на `duration_api_ms` — считает `tool_wall_ms` прямой суммой пар `tool_use`/`tool_result` транскрипта, `infra_ms` — её часть по классификатору BuildKit, `work_ms = tool_wall_ms − infra_ms`, `model_ms = wall_ms − tool_wall_ms` (все неотрицательны; на DooD совпадает со старым методом); базовые образы предзапечены в образ харнеса (`scripts/build-base-images-tar.sh` → `base-images.tar` → `docker load`), чтобы `pull` базы не попадал во время прогона. Разбор — [docs/incidents/2026-09-02-dind-timing-broken/](docs/incidents/2026-09-02-dind-timing-broken/README.md). Тикеты 1–9 (DooD) не затронуты; 4 прогона тикета 10 сделаны до почина — их `timing-breakdown.json` несёт поле `warning`, в журнале помечены «н/д». Первое подтверждение `infra_ms > 0` под DinD — тикет 11.

Сам журнал — [docs/EXPERIMENT-LOG.md](docs/EXPERIMENT-LOG.md).

Сравнительные отчёты между языками (`docs/PILOT-COMPARISON-*.md`) — обязательно показывать токены (in/cache-w/cache-r/out) и явно фиксировать модель/effort рядом с долларовой стоимостью, не только доллары: доллары сами по себе малоинформативны — конфлируют четыре категории токенов с разной ценой за единицу, и без явной фиксации модели/effort не видно, дрейф ли это цены API или дрейф конфигурации самого прогона (проверять по транскриптам, не полагаться на то, что раз задано один раз в скрипте — значит не менялось).

## Не делать

- Не переключаться на решение проблемы (Loop Engineering) — это отдельный доклад.
- Не отклоняться от `docs/SYNCBOX-SPEC.md` между языками — HTTP API и CLI зафиксированы буквально одинаково для всех семи; расхождение делает тикеты несравнимыми (см. пункт 3 в разделе «Сначала пилот»).
- Не подавать промежуточные результаты как доказанные выводы — CFP прямо обещает гипотезу и первые наблюдения к октябрю, не готовые выводы.
- Не подавать данные и выводы по OCaml/Scala/Golang как часть доклада RubyRussia 2026 — эти языки вне CFP, данные копятся для другого материала.
- Не запускать код тикета напрямую на хосте — только в Docker-контейнере (см. «Docker-изоляция» в `docs/SYNCBOX-SPEC.md`); без изоляции хостовые особенности (например, конкретная ОС и её файловая система) подмешиваются к измеряемому эффекту языка.
- Не использовать алиасы моделей (`sonnet`, `claude-sonnet-latest` и т. п.) — только точный ID (`claude-sonnet-5`) на каждом вызове; алиасы дрейфуют со временем, а дрейф версии модели — ровно то, что мы исключили сменой харнесса, не стоит возвращать его через другую дверь.
- Не полагаться на дефолт CLI для `--effort` — фиксировать `--effort xhigh` явно на каждом вызове, тем же принципом, что и точный ID модели. Найдено эмпирически 2026-08-24: харнесс до этой правки не передавал `--effort` вообще, и дефолт CLI сам сдрейфовал между версиями Claude Code — 6 прогонов пилота (Python+Go, переигрывались на Docker-харнессе) оказались под `effort=high` вместо `xhigh`, задокументированного для более ранних прогонов; обнаружено только `grep`-проверкой по `effort` в архивированных `transcript.jsonl`, не по документации или `--help`. Переиграны ещё раз под явным `--effort xhigh`.
- Не гонять контракт-гейт с `/data` на bind-mount на macOS — только tmpfs (compose-override в `scripts/run-gates.sh`). Bind-mount возвращает virtiofs-недетерминизм Docker Desktop, и провал контракта перестаёт быть сигналом о коде (замерено 2026-08-31: 2–7 падений из 8 на идентичном входе; на tmpfs JS/TS дают 8/8). Не пинить schemathesis версией — та же причина: генератор не должен дрейфовать между прогонами.
