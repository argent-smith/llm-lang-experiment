# Эталонная реализация (только для CI)

Служебный код, не один из шести языков эксперимента. Единственная задача —
дать [../smoke.sh](../smoke.sh) заведомо правильную реализацию Syncbox,
чтобы в CI ловить регрессии в самом acceptance-тесте, а не в языках
эксперимента. Реализации шести языков эксперимента живут в отдельных
репозиториях, не здесь — см. «Полигон» в [../../CLAUDE.md](../../CLAUDE.md).

Написано на Python исключительно потому, что интерпретатор гарантированно
есть в любом CI-окружении без установки — это не связано с тем, что Python
входит в число языков эксперимента.

Запуск: `run-server --data-dir <path> --port <n>` и
`run-client <push|pull|sync|status> <dir> --server <url>` — конвенция из
[SYNCBOX-SPEC.md](../../docs/SYNCBOX-SPEC.md).

## Docker-изоляция

Оба процесса — сервер и клиент — исполняются внутри Docker-контейнеров
(`Dockerfile`, `python:3.12-slim`), не напрямую на хосте: обязательное
требование для всех «стендов» эксперимента, см. раздел «Docker-изоляция»
в [SYNCBOX-SPEC.md](../../docs/SYNCBOX-SPEC.md). Внешний контракт
`run-server`/`run-client` не меняется — Docker целиком внутри обёрток
(`run-server`, `run-client`, общий `_docker.sh`).

Механика связи клиент↔сервер: контейнер сервера называется
детерминированно по порту (`syncbox-reference-server-<port>`) и
публикует этот порт наружу (`-p`) — так его видит хост (curl из
smoke.sh/contract-test.sh). Контейнер клиента подключается не к хосту,
а к сетевому namespace контейнера сервера через
`--network container:<то же имя>`, вычисляя порт из `--server` URL —
тогда `127.0.0.1:<port>` внутри контейнера клиента означает ровно то же,
что и снаружи, без host-networking. Причина обходить `--network host`:
на Docker Desktop для macOS он не пробрасывает порт контейнера на хост
(проверено на практике) — этот путь понадобился бы только если убирать
явный `-p`.

**Известная особенность локального запуска на macOS.** Docker Desktop
делит файлы с контейнером через VirtioFS/gRPC-FUSE, а не напрямую —
после записи на хосте свежесозданный контейнер иногда видит устаревшее
содержимое смонтированного файла (задержка консистентности на уровне
самого Docker Desktop, воспроизводится даже без нашего кода: `docker run
--rm -v $DIR:$DIR alpine cat $DIR/file` сразу после правки на хосте).
Из-за этого один пункт smoke.sh (`09-server-has-updated-content-after-
sync`) может ложно падать локально на Mac: клиентский контейнер читает
файл до правки, решает, что синхронизировать нечего. На Linux (CI,
вероятно и Replit) bind-mount — это тот же файл ядра без VM-прослойки,
и такой задержки нет — CI является источником истины для этого теста.
