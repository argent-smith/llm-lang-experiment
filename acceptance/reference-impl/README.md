# Эталонная реализация (только для CI)

Служебный код, не один из шести языков эксперимента. Единственная задача —
дать [../smoke.sh](../smoke.sh) заведомо правильную реализацию Syncbox,
чтобы в CI ловить регрессии в самом acceptance-тесте, а не в языках
эксперимента. Реализации шести языков эксперимента живут в отдельных
репозиториях, не здесь — см. «Полигон» в [../../CLAUDE.md](../../CLAUDE.md).

Написано на Python исключительно потому, что интерпретатор гарантированно
есть в любом CI-окружении без установки — это не связано с тем, что Python
входит в число языков эксперимента.

Запуск: `run-server --data-dir <path> --port <n>` и
`run-client <push|pull|sync|status> <dir> --server <url>` — конвенция из
[SYNCBOX-SPEC.md](../../docs/SYNCBOX-SPEC.md).

## Docker-изоляция

Оба процесса — сервер и клиент — исполняются внутри Docker-контейнеров
(`Dockerfile`, `python:3.12-slim`), не напрямую на хосте: обязательное
требование для всех «стендов» эксперимента, см. раздел «Docker-изоляция»
в [SYNCBOX-SPEC.md](../../docs/SYNCBOX-SPEC.md). Внешний контракт
`run-server`/`run-client` не меняется — Docker целиком внутри обёрток,
и всё Docker-хозяйство идёт через **docker compose**
(`docker-compose.yml`), не через голые `docker run`/`docker build`.

Механика связи клиент↔сервер: сервер публикует порт наружу (`-p`) — так
его видит хост (curl из smoke.sh/contract-test.sh). Клиент — в обычной
сети проекта compose (создаётся автоматически для всех сервисов, без
дополнительных флагов) и обращается к серверу по имени сервиса
(`http://server:<port>`), которое резолвит встроенный DNS compose.
Оба сервиса запускаются в рамках одного `--project-name`, детерминированно
выведенного из порта (`project_for_port` в `_docker.sh`) — так `run-client`,
зная только `--server` URL, попадает в сеть именно того проекта, что
поднял `run-server`.

Альтернатива `network_mode: "service:server"` (клиент делит сетевой
namespace с сервером — тогда `127.0.0.1:<port>` совпадало бы для хоста и
контейнера) была опробована и отклонена: `network_mode` в этом виде
требует, чтобы сервис-цель уже был запущен для самого сетевого
прикрепления — `docker compose run client` тихо поднимал `server`, даже
когда тот намеренно не должен был существовать (тест на «сервер
недоступен» проверял не то). С обычной сетью недостижимость — честный
провал DNS/подключения, без побочных автозапусков.

**О локальном запуске на macOS.** При разработке на Docker Desktop
воспроизводился баг file-sharing (VirtioFS/gRPC-FUSE): свежесозданный
контейнер иногда видел устаревшее содержимое bind-mounted файла сразу
после записи на хосте — воспроизводилось даже без нашего кода (`docker
run --rm -v $DIR:$DIR alpine cat $DIR/file`). Под текущей
compose-обвязкой это не проявилось на нескольких чистых прогонах подряд
— возможно, задержка на `--build` перед каждым вызовом клиента просто
уводит от гонки, а не устраняет её первопричину на уровне Docker
Desktop, так что при подозрении на повтор ориентируйтесь на CI (Linux,
без VM-прослойки в bind-mount), а не на единичный локальный результат.
